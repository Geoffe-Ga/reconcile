## 6. Relay API

#62 builds it: FastAPI on Uvicorn, with SQLite in WAL mode ([ADR-0028](../../adr/0028-relay-fastapi-sqlite.md)), behind Caddy on one VM ([ADR-0041](../../adr/0041-digitalocean-relay-hosting.md), #68). The relay stores opaque blobs by mailbox id and returns them in order with their receipt minute. The unguessable mailbox id is the only capability: there are no accounts or tokens (ADR-0073).

| Method | Path | What it does |
|---|---|---|
| `PUT` | `/v1/mailbox/{id}?ttl_days=N&wake=1` | Stores one raw `application/octet-stream` blob and returns `201 {"seq": n}`. `wake=1` (optional) asks for a push |
| `GET` | `/v1/mailbox/{id}?after=S&limit=L` | Returns `{"records": [{"seq", "received", "data"}], "now", "instance"}` |
| `GET` | `/v1/health` | Returns `{"status": "ok"}` |
| `GET` | `/v1/push/key` | Returns `{"vapid_public_key": k}`: the relay's P-256 point, uncompressed, as 87 unpadded base64url characters (#89) |
| `PUT` | `/v1/push/{id}` | `{"endpoint": url}` registers a push endpoint under the mailbox for 30 days, or refreshes it, and returns `204` |
| `DELETE` | `/v1/push/{id}` | `{"endpoint": url}` forgets it, and always returns `204` |
| `POST` | `/v1/push/{id}/nudge` | `{"not_before": minute}` schedules a wake in that relay minute, or now if it has passed, and returns `204` |
| `PUT` | `/v1/backup/{id}` | Stores one raw `application/octet-stream` backup, replacing any earlier one, and returns `204` (#97) |
| `GET` | `/v1/backup/{id}` | Returns the backup's bytes as `application/octet-stream`, or `404 {"error": "not_found"}` |
| `PUT` | `/v1/shelf/{address}` | Stores one public shelf record its address signed and returns `201 {"seq": n}` (#484), or `200` with the first copy's seq for a repeated entry or withdraw (#431) |
| `GET` | `/v1/shelf?after=S&limit=L` | Returns `{"records": [{"seq", "received", "address", "data"}], "now", "instance"}`: every shelf record that isn't held (#484) |
| `GET` | `/v1/shelf/held?after=S&limit=L` | The same shape, for held records only: the steward's console reads it (#488) |

- **PUT.** The id matches `^[A-Za-z0-9_-]{43}$`, the body is exactly 1,024, 4,096, 16,384 or 65,536 bytes, and `ttl_days` is 1–30. `Content-Length` is required and at most 65,536, and the relay checks it before reading. Anything else gets a 4xx and stores nothing. Once the database and its WAL pass `RECONCILE_RELAY_MAX_DB_BYTES` (default 1 GiB), a PUT gets `507 {"error": "storage_full"}`. Then a PUT that would take its mailbox's unexpired blobs past `RECONCILE_RELAY_MAX_MAILBOX_BYTES` (default 64 MiB) gets `507 {"error": "mailbox_full"}`, so no one mailbox can fill the relay (#141). Both caps are checked on the declared length before reading, and the mailbox cap again just before the insert. A full mailbox makes room only as its blobs expire.
- **GET.** `after` is at least 0 (default 0), and `limit` is 1–100 (default 100). Records come in ascending seq order, after `after`, unexpired, with `data` in standard base64. An unknown mailbox returns an empty list, never a 404. The relay reads `now` before it selects, so every record a response leaves out has `received` ≥ `now`.
- **Order and time.** `received` and `now` are relay minutes, ⌊Unix seconds / 60⌋. `seq` only grows, even after a purge empties a mailbox. `instance` is 16 random bytes made with the database, so a client can tell when it meets a fresh relay. The relay is trusted for this order and time (ADR-0073), and for nothing else.
- **Storage.** One table, `blobs(mailbox, seq, blob, received, expiry)`, plus a `meta` row for `instance`. `expiry` is the UTC day of receipt plus `ttl_days` plus 1, and a row expires once today reaches it. A GET skips expired rows, and a daily purge deletes them. Push adds two tables (#89): `push_subs(mailbox, endpoint, expiry)` and `nudges(mailbox, due)`, both `WITHOUT ROWID`, keyed on all but `expiry`, with no push keys, timestamps or counters. An index on `(mailbox, expiry, length(blob))` sums a mailbox's bytes for its cap without reading a blob (#141). Any new column needs an ADR.
- **Backups** (#97, ADR-0043 §3, [ADR-0072](../../adr/0072-protocol-details-for-decomposition.md) items 13 and 14). The id follows the mailbox rule (else `400 invalid_backup`), and the body is `application/octet-stream` of exactly 65,536, 262,144, 1,048,576, 4,194,304 or 16,777,216 bytes. `Content-Length` is required and at most 16,777,216, checked before reading, as for a blob, and the relay's `storage_full` applies; the mailbox cap counts blobs only. One table, `backups(id, blob, expiry)`, `WITHOUT ROWID`, keyed on `id`, every column `NOT NULL`, with an index on `expiry` for the purge and no receipt time. A PUT replaces the row, and `expiry` is the UTC day of the write plus 181, so a backup is kept 180 days after its last refresh. A GET doesn't refresh it, skips it from its expiry day, and the daily purge deletes it. There is no DELETE: a backup goes when it expires.
- **Push** (#89, [ADR-0012](../../adr/0012-content-free-push.md)). It is on only when `RECONCILE_RELAY_VAPID_KEY` names a PEM P-256 private key, which deploy.sh makes once on the VM ([`deploy/README.md`](../../../deploy/README.md)). `RECONCILE_RELAY_VAPID_SUBJECT` must then be `https://<domain>` or `mailto:<address>`, never `localhost` or an IP address, or the relay won't start. Without a key, every push route returns `404 {"error": "push_unavailable"}` and `wake` does nothing.
  - **Requests.** The push routes take `application/json` (else 415) with a declared `Content-Length` of at most 2,048 bytes, checked before reading. A body is one UTF-8 object holding exactly its one key, of its type, with no duplicate key (else `400 invalid_request`). Mailbox ids are checked as for a blob. A push PUT or nudge gets the blob PUT's `storage_full`; a DELETE doesn't, and the mailbox cap counts blobs only. `wake` is `1` or absent (else `400 invalid_wake`, checked before the body).
  - **Endpoints.** At most 1,024 bytes of printable ASCII: `https`, no userinfo, fragment, backslash or space, port absent or 443, and a lower-case host that is `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com`, or under `push.apple.com` or `notify.windows.com`. Every failure gets the same `422 {"error": "push_endpoint_rejected"}` and stores nothing. `expiry` follows the blob rule with 30 days, and a re-PUT refreshes it. A mailbox holds at most 100 endpoints; the 101st evicts the one expiring soonest, never itself.
  - **Nudges.** `not_before` is a relay minute from 0 to now + 43,200 (else `400 invalid_not_before`). A mailbox holds at most 50 pending nudges (else `429 too_many_nudges`), and a repeated minute is no new one. `wake=1` adds a nudge due in the blob's own `received` minute once the blob is stored, past the cap, and only if the mailbox has a live endpoint to wake.
  - **Sending.** Every 15 s the relay takes and deletes the due nudges, then sends one empty POST to each live endpoint of those mailboxes, each endpoint once however many of its mailboxes are due. The headers are exactly `TTL: 86400`, `Urgency: normal`, `Topic: reconcile` and RFC 8292's VAPID `Authorization` (`aud` the endpoint's origin, `exp` 12 hours on, `sub` the subject), over `httpx2` with no redirects, no cookies, no environment, 5 s to connect and 10 s in all. 201 or 202 succeeds, 404 or 410 deletes the endpoint from every mailbox, and anything else, an exception included, keeps it with no retry. Nothing is logged. The daily purge deletes expired endpoints, and nudges left more than a day overdue.
- **The public shelf** (#484, [ADR-0081](../../adr/0081-listed-doors-and-exception-moderation.md), [`listed-doors.md`](../listed-doors.md) §4). It is on only when `RECONCILE_RELAY_SHELF_STEWARD_KEY` holds the steward's Ed25519 public key in canonical unpadded base64url (else the relay won't start). Without it, both routes return `404 {"error": "shelf_unavailable"}` before checking anything else. Its records are the only bodies the relay can read (§9).
  - **Records.** A record is the 64-byte Ed25519 signature over the UTF-8 tag `reconcile/v1/shelf`, one 0x00 byte and the message, then the message: the record's compact UTF-8 JSON. The signer is the key the record is PUT under, a listed door's `sign` key for a group's records, so the record doesn't carry its address. This slice stores `listing` (`{v: 1, kind, open: true, name, skeleton, covenant}`, or `{v: 1, kind, open: false, final: true}`), `entry` (`{v: 1, kind, id, title, text}`), `withdraw` (`{v: 1, kind, id}`) and the steward's `notice` (#488, below). `client/src/crypto/vectors/shelf.json` pins the format.
  - **PUT.** In order: the address is 43 characters of canonical unpadded base64url, a 32-byte key (else `400 invalid_address`); the body is `application/octet-stream` (else 415); `Content-Length` is required and at most 4,096, checked before reading (else 411 or `413 too_large`); the relay's `storage_full` applies; and a PUT that would take the shelf's unexpired records past `RECONCILE_RELAY_SHELF_MAX_BYTES` (default 64 MiB) gets `507 {"error": "shelf_full"}`, checked on the declared length and again just before the insert. Then the body holds a signature and at least one byte of message (else `400 invalid_record`), the signature verifies against the address (else `403 bad_signature`), the message is a v1 `listing`, `entry`, `withdraw` or `notice` object, with no key twice, an `entry` or `withdraw` naming a text `id` and a notice naming all its act names (below; else `400 invalid_record`), and the record is at most 1,024 bytes for a listing, withdraw or notice, or 4,096 for an entry, signature included (else `413 too_large`). A notice PUT under any address but `RECONCILE_RELAY_SHELF_STEWARD_KEY` gets `403 bad_signature`, whoever signed it. A listing must be open (`open` is `true`) or final (`open` is `false` and `final` is `true`), else `400 invalid_record`. The relay reads nothing else of it: never a name, a title or a text.
  - **Listings** (#486). An address has one listing. A later copy takes the earlier one's row in place: its body, receipt and expiry, keeping its `seq` and its hold, so the listing keeps its first place in the shelf's order and expires 30 days after its last post. An open listing PUT where a final one stands gets `409 {"error": "listing_final"}` and changes nothing; a final one again renews it. A final listing deletes every other record under its address, its entries and withdraws. Looking up an address's listing scans the table: no index is on an address.
  - **Entries** (#431; [`listed-doors.md`](../listed-doors.md) §4.2). An `entry` or `withdraw` needs a live listing at its address: an open one that hasn't expired (else `409 {"error": "not_listed"}`, a final or lapsed listing included). A repeat, the same kind with the same address and id while the first copy is unexpired, stores nothing and returns `200 {"seq": n}` with the first copy's seq, whatever its text; so an id an address withdrew never comes back while the withdraw stands. A withdraw names an unexpired entry of its own address (else `409 {"error": "no_entry"}`), so withdraws stay as few as entries. A new entry fits two caps (else `429 {"error": "too_many_entries"}`): at most 4 live entries per address, where an entry is live until it expires or a withdraw from its address names it, and at most 1 new entry per address each UTC day, a withdrawn one still counting for its day. An entry is kept 30 days after its first post, as every record. The checks run in that order, after the signature and size checks, and read only `kind`, `ref`, `received` and `expiry`, never a title or a text.
  - **Skeletons and name ownership** (#487; [`listed-doors.md`](../listed-doors.md) §4.3 rules 3 and 4, §4.4). An open listing's `skeleton` is `nameSkeleton(name)` (`client/src/shelf/skeleton.ts`): NFKC; case folding, as upper case then lower case with `ς` as `σ`; removal of `White_Space`, punctuation (`P`) and `Default_Ignorable_Code_Point`; then UTS #39's skeleton (NFD, each code point to its prototype in `client/src/shelf/confusables.ts`, NFD), and those steps again until nothing changes, at most 3 passes. `confusables.ts` is every mapping in Unicode 18.0.0's `confusables.txt`, written by `client/scripts/confusables.mjs`, which checks the file's SHA-256; `skeleton.test.ts` pins the table's. The fold (`foldShelf`) ignores an open listing whose `skeleton` isn't its name's, as if it were never posted. Among standing listings that share a skeleton, the one whose claim has the lowest `seq` holds the name, then the lower address; the others are shadowed, and neither they nor their entries show. A door's claim starts at the first copy of its newest unbroken run of listings under that skeleton. `client/src/shelf/vectors/skeleton.json` and `ownership.json` pin both. Skeletons are computed on the device from public names: the relay stores the field and never reads or compares it.
  - **Held mode and the steward's release** (#488; [`listed-doors.md`](../listed-doors.md) §4.2, §6.1, §6.2). `RECONCILE_RELAY_SHELF_MODE` is `held`, the only mode built; unset or empty means `held`, and any other value stops the relay (open mode is deferred, §9). An address's first listing is stored held, `held_until` = 2⁶³ − 1, a minute no clock reaches; a later copy keeps its row's hold; and an entry or withdraw PUT while its address's listing is held is stored held too. A `release` notice, `{v: 1, kind: "notice", act: "release", address}`, signed by the steward's key and PUT under it, is stored with `ref` = the address it names, kept 180 days, and clears the hold of every record at that address; whatever comes after is stored live. A renewal of a listing keeps every release notice naming its address at least as long as the listing, so a released listing never outlives its release. Once a listing's row is purged, its address's next listing is a first listing, held again. The two public keys the app pins (`client/src/shelf/steward.ts`, `sign` and `box`, §6.2) both derive from the steward's one 32-byte secret by HKDF-SHA-256 with an empty salt, under `reconcile/v1/steward-sign` (Ed25519, the relay's key) and `reconcile/v1/steward-box` (X25519, for reports, §6.3); `python -m scripts.steward_key` makes one offline, and `client/src/crypto/vectors/steward.json` pins the derivation.
  - **The steward's later notices** (#489; [`listed-doors.md`](../listed-doors.md) §6.1). Each is PUT under the steward's key and signed by it, as a release is, and names exactly what its act acts on (else `400 invalid_record`): a `hold` an `address`, a `clause` (`C1`, `C2` or `C3`) and, to hold one entry rather than the whole listing, that entry's `id`; an `uphold` an `address`, an `id` and a `clause`; a `suspend` an `address` and a `clause`; and a `pause` `on`, `true` or `false`. §6.1 says a pause is "on or off" and §4.1's body had no field for it, so #489 adds `on`, on a pause only: `{v: 1, kind: "notice", act: "pause", on}`. Every id and address is a canonical 43-character key. A notice is filed under a `ref` that names what it acts on: a release under its address, as before, and the others under `hold:{address}`, `hold:{address}:{id}`, `uphold:{address}:{id}`, `suspend:{address}` or `pause`.
    - **Hold.** Every record at the address, or only that entry, is held until the notice's minute plus 10,080, never shortening a longer wait; a held record leaves `GET /v1/shelf` for `GET /v1/shelf/held`, and comes back once that minute arrives, with no uphold needed to end it. Whatever is PUT under a held address meanwhile waits with its listing. A release leaves a hold that stands: records waiting for the release are held until the newest standing hold on their address lapses, else not at all. A hold is kept 180 days.
    - **Uphold.** The address needs a live entry with that id (else `409 {"error": "no_entry"}`, and nothing is stored); the relay deletes it and any withdraw of it, and keeps the notice exactly as long as the entry would have been kept, its expiry the entry's. While the notice stands, the same entry PUT again gets `403 {"error": "upheld"}`, so a member's device never brings it back.
    - **Suspend.** The relay deletes every record at the address, and while the notice stands (180 days) every PUT under that address gets `403 {"error": "suspended"}`, checked before the body is read. Once the notice expires, the address is a new one, and its next listing is held for release.
    - **Pause.** Stored, kept 180 days, and nothing else: the relay serves everything as before, and devices fold it.
  - **The fold's notices** (#488, #489; §4.3 rules 1 and 8, `client/src/shelf/fold.ts`, `notices.ts`). A device counts a notice only when it came under the steward's address pinned in `client/src/shelf/steward.ts` and verifies against that key (`foldNotices`); with no key pinned, none counts, so nothing a person sees changes. A listing stands only once a counted release names its address: until then it shows nowhere, claims no name and shows no entries, so a relay that served an unreleased listing still couldn't show it. Then, in seq order: the latest **hold** on each listing or entry hides it, a listing's with every entry under it, while relay minute `now` is under the notice's `received` plus 10,080 (`HOLD_MINUTES`); held at 10,079, shown again at 10,080. A held listing keeps its name, so no look-alike shows in its place meanwhile, and its entries still count toward its 4. `ShelfState.holds` lists each hold that stands. An **uphold** hides its entry for good, frees its place among the 4 (the relay deleted it), and leaves a tombstone `{address, id, clause, seq}` in its place while its listing shows, until the entry's 30 days end: from the entry's own receipt when this device read it, else from the uphold's, which can only end sooner. A **suspend** ends its address's listing, with its name and entries, whatever the relay still serves; the first suspend of an address names its clause, and, once a release had let the listing show, it leaves a tombstone with `id` null for 30 relay days, as long as a listing that posts nothing more is kept. The newest **pause** sets `paused`. `doorListing(records, address, now)` is held while no release names the listing, a hold on it stands (counted from the hold itself when the relay withholds the listing meanwhile), or it is suspended, and then carries the clause as `removed`; #432's rule offers no Documents to any of them. `standingHolds` names each standing hold's listing and entry for the console. The keeper (`shelf/keeper.ts`) posts nothing more under a suspended address and never posts an upheld entry again, and a relay's `403 suspended` or `403 upheld` stops it the same way. `client/src/shelf/vectors/notices.json` pins rule 8: each notice, and the lapse at 10,079 and 10,080 minutes.
  - **GET.** `after` and `limit` as for a mailbox. Records from every address come in ascending seq order, unexpired and not held, each with the address it was PUT under and its bytes in standard base64. `now` is read before the select. `GET /v1/shelf/held` pages the held records alone, the same way.
  - **Storage.** One table, `shelf(seq, address, kind, ref, body, received, expiry, held_until)`, every column `NOT NULL`, `seq` an `AUTOINCREMENT` key of its own. `ref` is an entry's or withdraw's id, else empty. `expiry` is the UTC day of receipt plus 31, so a record is kept 30 days, and `held_until` is the minute a record is held until, 0 for one that isn't. A notice's `ref` names what it acts on (above); its `expiry` is the UTC day of receipt plus 181, an uphold's the entry's own. One index, on `(expiry, length(body))`, serves the purge and the shelf's byte cap, and none is on an address. The daily purge deletes expired records.
- **Never.** Errors are a constant `{"error": "<code>"}` that never echoes input. There are no docs routes, no debug route, no CORS (the app and relay share one origin) and no request logs. The outermost ASGI middleware sets `scope["client"]` to `None` and deletes forwarding headers before routing. Uvicorn runs one worker with `--no-access-log --no-proxy-headers --no-server-header`. The relay's only outbound requests are pushes.
