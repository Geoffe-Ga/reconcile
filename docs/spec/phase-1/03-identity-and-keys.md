## 3. Identity and keys

[ADR-0009](../../adr/0009-per-group-identities.md), as ADR-0073 cut it: every membership has its own random keys, with no root identity behind them.

- **Signing keys** (#69). Create group and Join each make a fresh Ed25519 keypair, stored with that group's records only. An event's `author` is the public key in unpadded base64url (43 characters). The secret key stays in the store: the actions read it there to sign, and no screen is handed it. Store version 2 brought these keys in and deleted the stub era's unsigned data on upgrade, with no migration.
- **Records** (#69). A record is `publicKey (32 bytes) ‖ signature (64) ‖ event bytes`. The signature covers UTF-8 `reconcile/v1/event` ‖ `0x00` ‖ event bytes. `sign(ctx, secretKey, msg)` and `verify(ctx, publicKey, sig, msg)` in `src/crypto/sign.ts` take the tag as a typed parameter, and an invite token signs under its own tag, `reconcile/v1/invite-token` (#73). Verification calls `ed25519.verify(sig, msg, pub, { zip215: false })`, never the library default, which accepts non-canonical encodings and small-order keys. The outbox and the log hold records. Every check that passes, of a record's signature, an invite token, a seat proof, a share's copy or a door's page, keeps its verdict for the page's life, in memory only and never on disk, by the SHA-256 of the key, the signature and the tagged message, so a re-fold verifies none of them again (#362). A failure is never kept: it runs again each time, so junk a mailbox holds can't grow the set.
- **Group secret** (#71). Genesis makes 32 random bytes that only members hold. The group's other values derive from it with HKDF-SHA-256, an empty salt and 32 bytes of output (`src/crypto/groupKeys.ts`, pinned by `src/crypto/vectors/derive.json`):
  - each relay week's mailbox id (#110), in unpadded base64url, with info UTF-8 `reconcile/v1/mailbox-week` ‖ `0x00` ‖ the week as 4 big-endian bytes (`deriveWeekMailboxId`). The week of relay minute `m` is ⌊m / 10,080⌋ (`weekOf`), so weeks turn over on Thursday at 00:00 UTC, and it comes from the relay's `now` only, never the device clock. It replaced M2-02's one id per secret (info `reconcile/v1/mailbox`) for all group traffic; an invite's mailbox is its own;
  - the seal key, with info `reconcile/v1/seal-key`, the same in every week of the secret's epoch. The mailbox id stays a blob's associated data (Seal, below), so a blob can't be moved to another week;
  - each coalition motion's nudge offset (#284, §4 Coalitions, Push), with info UTF-8 `reconcile/v1/nudge-offset` ‖ `0x00` ‖ UTF-8 motion id, the 43 characters its event spells, and 4 bytes of output read big-endian, modulo 60 (`nudgeOffset`, `src/crypto/nudgeOffset.ts`, pinned by `src/crypto/vectors/nudge-offset.json`, computed outside @noble): the whole minutes, 0 to 59, the group's nudges for that motion shift by.

  The store keeps only the secret, at store version 3, and derives the rest where it's needed. Version 3 deleted older data, whose relay blobs anyone could read, on upgrade, with no migration.
- **Encryption keys** (#98; ADR-0009, ADR-0074). Create group and Join also make a random X25519 keypair for that one group (`src/crypto/box.ts`), kept in the group's record beside its signing key (`kxKey`) and in the backup file. `genesis` and `join` carry its public half as `kx`, in unpadded base64url, and the fold records it on the member. A device whose member has no `kx`, as one that joined before #98, posts `kx` once. A **box** seals a plaintext to one X25519 public key: a fresh ephemeral key, `dh = X25519(ephemeral, public key)` (a low-order key, whose `dh` would be all zeros, is refused), `k = HKDF-SHA-256(dh, salt = ephPub ‖ public key, info, 32)`, and `ephPub (32) ‖ nonce (24) ‖ XChaCha20-Poly1305(k, nonce, aad)(plaintext)`; `openBox` returns null for every failure alike (pinned by `src/crypto/vectors/box.json`, sealed outside @noble and opened again by libsodium). #109's recovery shares reuse it. The group's secret has an **epoch**, 0 from genesis, and each new one is committed to and wrapped as §4 says (`src/crypto/epoch.ts`, pinned by `vectors/epoch.json`). A group kept before #98 reads as epoch 0, so the store version stays 3.
- **Seal** (#64, #71). XChaCha20-Poly1305 (`@noble/ciphers`) under the seal key, with the mailbox id's UTF-8 as associated data. A blob is a random 24-byte nonce, then the ciphertext of (a 4-byte big-endian length ‖ the payload ‖ zeros up to the size less 40), then a 16-byte tag, in the smallest of the four sizes where the payload is at most the size less 44. A payload is at most 65,492 bytes. `open` authenticates first, and returns null alike for a wrong size, key or mailbox, any changed byte, or a length that runs past the frame. A blob that fails to open is skipped, and the cursor still moves past its seq. `createSync` takes the seal as a required option, and the frame-alike stub is a test fixture in `src/test/` that the app can't import (#151).
- **Largest record** (#71). Create group, the composer and a new version (#72) build the real record and refuse it, tied to the field, when it's over 64,000 bytes, counting bytes, not characters. The store refuses one too. The margin below 65,492 lets #73 carry any record, with its seq and receipt time, in one invite chunk.
- **Invite seed** (#73). Copy invite link makes a random 32-byte seed, and the invite mailbox id and key derive from it through the same HKDF, with infos `reconcile/v1/invite-mailbox` and `reconcile/v1/invite-key` (`src/crypto/invite.ts`, pinned by `src/crypto/vectors/invite.json`, computed outside @noble). The link is `${origin}/#join/${seed}`, 43 base64url characters, so the seed never reaches a server, and the group secret travels only inside the sealed envelope (§7). `parseInviteLink(text)` returns the 32-byte seed, or null, for a whole link from any origin or the bare seed, so Start's paste field reads invites the same way. The tracer's `#/join/{payload}` form still routes to Join, where it shows the expired-or-damaged line.
- **Seat proof** (#100; ADR-0009, ADR-0036). A group that reconciles makes a **seat**: an Ed25519 keypair whose secret sits in its reconcile Proposal, so only its sealed log holds it, and whose public key the coalition's genesis names. A participant joins the coalition under a fresh key and name of their own, never their group key, and carries `sign('reconcile/v1/seat', seatSecret, UTF-8 coalition id ‖ 0x00 ‖ joiner's 32-byte public key)` (`src/crypto/seat.ts`, checked against WebCrypto). It shows the group, never the person: anyone holding the seat secret can make one.
- **Card seed** (#114, §4 Coalitions). Reconcile with another group makes a random 32-byte seed. The card mailbox id and key derive from it through the same HKDF, with infos `reconcile/v1/card-mailbox` and `reconcile/v1/card-key` (`src/crypto/card.ts`, pinned by `src/crypto/vectors/card.json`, computed outside @noble). The link is `${origin}/#reconcile/${seed}`, so the seed never reaches a server. `parseCardLink(text)` returns the seed, or null, for a whole card link from any origin; a bare seed is an invite's. A device keeps each coalition it holds a secret of under an **entry id**, HKDF of the coalition secret with info `reconcile/v1/coalition-entry`, so every device and tab finds one entry per coalition before its genesis exists. The entry id never leaves the device but in a backup file.
- **Room keys** (#125, §4 Coalitions). A coalition's room has the weekly mailbox ids and seal key a group secret would, derived the same way from the coalition's `inner` (`deriveWeekMailboxId`, `deriveSealKey`), which only seated groups hold, so a follower (#124), who holds the coalition secret alone, derives neither. A device keeps the room under an entry id, HKDF of `inner` with info `reconcile/v1/room-entry` (`src/crypto/room.ts`, all pinned by `src/engine/vectors/room-keys.json`, computed and sealed outside @noble). No backup file, link bundle or relay backup carries a room.
- **Room wraps** (#313, §4 Coalitions). A group admitted into a formed coalition receives `inner` through its seat. The seat's X25519 secret key is HKDF of its 32-byte seat secret with info `reconcile/v1/seat-kx` (`seatKxKeyOf`), and its admit motion carries the public key as `kx` (`seatKxOf`). A wrap is a box (`box.ts`) of `inner` sealed to that key with info `reconcile/v1/room-wrap` and associated data UTF-8 coalition id ‖ 0x00 ‖ UTF-8 seat key, the two texts as events spell them (`wrapInner`), so a wrap moved to another seat or coalition never opens. `unwrapInner` opens it with the seat secret, and answers null for anything but 32 bytes, and for any `inner` but the one the coalition's genesis commits to (#371): `commit`, the base64url SHA-256 of UTF-8 `reconcile/v1/room-commit` ‖ `0x00` ‖ the 32 bytes of `inner` (`roomCommit`). `src/crypto/vectors/room-wrap.json` pins the derivation and two wraps, and `room-commit.json` the commitment, all made outside @noble.
- **Follow seed** (#124, §4 Coalitions, Following). Share a follow link makes a random 32-byte seed. The follow mailbox id and key derive from it through the same HKDF, with infos `reconcile/v1/follow-mailbox` and `reconcile/v1/follow-key` (`src/crypto/follow.ts`, pinned by `src/crypto/vectors/follow.json`, computed outside @noble). The link is `${origin}/#follow/${seed}`, so the seed never reaches a server. `parseFollowLink(text)` returns the seed, or null, for a whole follow link from any origin; a bare seed is an invite's.
- **Share seed** (#105, §11 Share link). Share link makes a random 32-byte seed and a fresh Ed25519 keypair for one personal Document, used for nothing else. The share mailbox id and seal key derive from the seed through the same HKDF, with infos `reconcile/v1/share-mailbox` and `reconcile/v1/share-key` (`src/crypto/share.ts`, pinned by `src/crypto/vectors/share.json`, computed outside @noble), and each copy is signed under its own tag, `reconcile/v1/share`. The link is `${origin}/#share/${seed}.${publicKey}`, so neither reaches a server.
- **Invite token** (#73). `{by, sig}`: the inviter's public key and `sign('reconcile/v1/invite-token', key, UTF-8 group id)`, both base64url, carried in the joiner's `join`. The fold sets the member's `invitedBy` to `by` only when the signature verifies and `by` was a member before the join. A token that is missing, malformed, from a non-member, over another group's id or signed under the event tag names no one and never invalidates the join (`src/engine/vectors/invite.json`, signed outside @noble).
- **Names** (#69; [ADR-0045](../../adr/0045-names-in-groups.md) as cut by ADR-0073). A name is fixed at join. When two members' names match after NFC, trimming and lowercasing, each shows ` · ` and the first 4 hex characters of the SHA-256 of its public key. Names render inside `<bdi>`.
- **Backup file** (#78; [ADR-0043](../../adr/0043-recovery-and-backup.md) and [ADR-0044](../../adr/0044-qr-device-linking.md) as cut by ADR-0073). One passphrase-sealed file holds every group's keys, secret and log, and every personal Document (#93), and nothing is uploaded.
  - The key is scrypt (N = 2^17, r = 8, p = 1, 32 bytes) over the NFC passphrase's UTF-8 and a random 16-byte salt (`src/crypto/backup.ts`). A passphrase has at least 8 characters, counted as graphemes after NFC.
  - The seal is XChaCha20-Poly1305 under a random 24-byte nonce, with the 47-byte header as associated data: `RCB1`, log2 N, r, p, the salt and the nonce. `src/crypto/vectors/backup.json` pins the format with a file sealed outside @noble.
  - `openBackup` refuses another magic, a log2 N above 20 (or r other than 8, or p other than 1) before deriving anything, and a failed tag after, all with one plain error.
  - The plaintext is JSON with bytes in unpadded base64url (`src/store/snapshot.ts`), at format 2 (#98). For each group it holds the secret and its epoch, the signing key, the encryption key, your name and author, the log's event bytes with their seqs, receipt times and, when it isn't 0, the epoch of the mailbox each was read from, the cursor, the last relay `now` and `instance`, the last successful sync time, the missing-history flag, and `cleared`, the Proposals whose ballots the device has deleted (#111, §7), when it has any. It leaves out the outbox and drafts, so a restore never sends stale intent, a group whose leave waits or whose genesis the relay hasn't returned, and a dissolved group's read-only copy (#108), whose ballots are due to be cleared, or the group to be erased, and which a file would keep past that, and a restored copy that hasn't heard from its group (#231, below), whose relay minute moves on with every pass, so a copy of it would look current. Beside `groups`, a `personal` list holds each personal Document whole: `{id, title, text, createdAt, updatedAt}` (#93), plus `share`, `{seed, secretKey, publicKey, n, lastPostedAt, pending}` with bytes in base64url, while it is shared by link (#105, §11), so a restore keeps the same link. The header stays as it was. A format 1 file, as #78 and #93 wrote it, still restores: every record at epoch 0 and no encryption key, which the sync loop then makes, unless the person's other device has already given the group theirs. Only the first `kx` per member counts (§4), so a device restored from such a file then never opens a wrap. So a restore reports whether the file is format 1 (`importGroups` and `replaceWithBackup` also return `older`, #225), and when it brought groups back from one, the restore form says, under how many came back: "This backup is from an older version of Reconcile. If you've used Reconcile on another device since you saved it, this device won't get a group's new key when someone leaves. Ask someone in that group for a new invite link then, or restore a newer backup saved on that device." A new invite link brings the current key (§4, No wrap); a format 2 file or a link from the other device carries the key that counts. A file of either format without `personal`, as every one before #93, holds no personal Documents, and a group without `cleared`, as every one before #111, has cleared nothing. A restore keeps the Proposals either copy has cleared, and none of what expired with them, so a file never brings a cleared ballot back.
  - Restoring reads at most 64 MiB, opens the file, and checks everything before it writes anything: every field's shape, that each signing key makes its author, that every record verifies, that each log folds to its own group, that a secret past epoch 0 is the one its epoch's key change commits to (#98), and that each personal Document is one the editor could have saved, each id once. Each group entry is checked on its own (#336): one that doesn't check out, or names a group an earlier entry that does already holds, is left out, the rest come back, and the restore says how many it left out (`importSnapshot`, `importGroups` and `replaceWithBackup` return `{groups, skipped}`). So one bad entry, which anyone else holding the passphrase or the relay backup key could plant, never keeps every other group from coming back. Anything else wrong (a format it doesn't read, a groups field that isn't a list, a personal Document or a backup key that doesn't check out) fails as a wrong passphrase does. It writes every group and personal Document in one transaction, and if any write fails, none stays. For a group already on the device, whichever whole copy synced later stays, and one this device is leaving or keeps read-only (#108) stays as it is. A group whose log in the file folds to a `dissolve`, as an older app's file could hold, comes back as a read-only copy that never syncs, so a restore never brings a dissolved group back to life. Every other group the restore takes comes back **read-only for now** (#231, [ADR-0051's 2026-11-11 amendment](../../adr/0051-dissolution-and-rule-classes.md)), since the group may have dissolved after the file was made and the relay may have let the `dissolve` go: `archived: {reason: "unconfirmed", since}`, `since` being the copy's `relayNow` (0 if it had none). It syncs as §7 says, and a coalition's entry, which never dissolves, comes back as it was. A personal Document merges by id the same way: the file's replaces the device's only when its `updatedAt` is later, so a tie keeps the device's. A file's copy with no share keeps the device's share, marked pending, so no live link is lost (#105). A share the file brings starts paused (#328, §11 Share link), since the file may predate Stop sharing: nothing posts to its link until the person keeps it. A restored group keeps the file's last sync time, so an old backup still shows the catch-up line (§7, #73).
  - Restoring it brings the groups back, or sets up a second device that votes as the same person: both hold the same per-group key, so the fold sees one voter, and the later ballot counts.
  - It also carries the device's relay backup key as `backupKey`, when the device keeps one (#97, ADR-0075 §4), and beside it, once the key has been split, the split's random 16-byte id as `backupSplit` (#272; never the contacts). A device restored from it keeps that key and split if it holds no key, so it keeps the relay backup fresh; one that holds a key keeps its own. A file without `backupKey` brings no key, one without `backupSplit` a key with no split, and a malformed key or split, or a split with no key, fails the restore.
- **Relay backup** (#97; [ADR-0043](../../adr/0043-recovery-and-backup.md) §3 as ADR-0074 revised it: a random backup key replaces the root key). An encrypted copy of every group on the device, kept on the relay so recovery contacts (#118) can bring them back after every device is lost.
  - **Key.** `startRelayBackup(services, {newKey})` (`src/store/relayBackup.ts`) makes a random 32-byte backup key when the device has none or `newKey` is set, keeps it device-wide in the store's `device` object store (store version 5, which adds it and deletes nothing), in no group (on a device whose keys are locked with a passkey, the record keeps its state and the vault its key, #95), uploads at once, and returns the replaced key's id, or null. #109 calls it, with `newKey` and the split the key is about to be cut into, whenever someone chooses contacts, and the state keeps that `split` beside the key (#272). No screen makes one before that. The key and its split travel in the backup file, above, and so in #96's link bundle, and never go to the relay, even sealed.
  - **A retired key** (#272, [ADR-0075 §4's 2026-11-12 amendment](../../adr/0075-safeguards-for-the-revised-mvp.md)). Every read of the relay copy before an upload, the daily refresh's and `startRelayBackup`'s with the key it holds, sorts what's under the id: a backup (`isRelayBackupBlob`: one of the five sizes, starting `RCR1`), which it merges or uploads over as before; nothing; or anything else, which only a choice of contacts on another of the person's devices writes there (Recovery contacts, below). That last means the key was retired: the device uploads nothing, and in one key transaction `retireRelayBackup` forgets the key and its state, the vault's copy included, keeps a `relay-backup-retired` mark with the device time, and marks a plan of its own superseded. It never uploads under that id again, and its later backup files and link bundles carry no key. A backup file, a link or a choice of contacts brings a key again and clears the mark.
  - **Id and seal** (`src/crypto/relayBackup.ts`, pinned by `src/crypto/vectors/relayBackup.json`, computed outside @noble). The id is the unpadded base64url of HKDF-SHA-256 of the key under `reconcile/v1/backup-id`, 43 characters; the seal key derives under `reconcile/v1/backup-seal`. A blob is `RCR1` ‖ a random 24-byte nonce ‖ XChaCha20-Poly1305 of (a 4-byte big-endian length ‖ the plaintext ‖ zeros) with its tag, in the smallest of 64 KiB, 256 KiB, 1 MiB, 4 MiB and 16 MiB that holds it, with `RCR1` ‖ the id's UTF-8 as associated data. `openRelayBackup` returns null alike for a wrong size, magic, key, any changed byte or a bad frame.
  - **Plaintext.** The backup file's plaintext without its passphrase layer, `backupKey` or `backupSplit`: `encodeSnapshot` of `deviceSnapshot`, the one place a snapshot is gathered, with the key and its split taken out. So the relay backup carries whatever a backup file does: format 2's keys and epochs (#98), so a restore from it lands each group at the epoch it held, and every personal Document (#93) with its share by link while it is shared (#105), so a device restored from it keeps the same link and can stop it, but never a dissolved group's read-only copy (#108), a restored copy that hasn't heard from its group (#231) or a push registration (#99). A restore from it merges personal Documents as a file's restore does, so a later copy with no share keeps the restoring device's share, marked pending (`restoredCopy`), and a share the copy brings starts paused (#328).
  - **Linked devices** (#247). A device linked by #96 takes the key, so linked devices keep one relay copy, while each keeps its own personal Documents. So before each upload the device GETs the copy under its id, opens it, reads its personal Documents and, of each group, only its id and author (`decodeRelayCopy`, which checks each Document as a restore does, leaves out and counts a group entry without a well-formed id or author (#336), and reads only a format 2 copy, as every relay copy has been), and uploads the union (`mergePersonal`, oldest first). A Document only one side holds goes as it is, unless only the relay copy holds it and this device has uploaded it before, so deleted it: the state notes `uploaded`, the id of every Document this device held at a successful upload, and a record from before #247 takes the relay copy's ids as its own. A Document both hold takes the later `updatedAt`, a tie keeping this device's, as a restore does (`keepsHeldCopy`), with this device's share by link (#105) if it has one, else the relay copy's while its link may still open, its last post under 30 days old (`mayStillOpen`), either marked pending when the words it carries changed (`keptShare`). So a restore from the copy brings back every Document either device wrote, the later edit of one both edited, and a linked device's live link, paused (#328), which the restored device can then keep or stop. A share this device stopped stays in the copy until its link can no longer open, so a device restored from it, even after the tombstone has lapsed, gets it back paused, and posts nothing to it unless the person keeps it. A GET that fails, a blob that doesn't open under the key, and one that holds no snapshot the device reads all leave nothing to merge: the device uploads its own copy as before #247, and nothing waits on the read. A Document deleted on one device but still kept on the other comes and goes from the copy as each refreshes, and neither device takes in the other's Documents.
  - **Groups on linked devices** (#327). Joins don't travel between linked devices, so a group one joins after the link is on that device alone. So the upload also carries the relay copy's entry for each group this device doesn't hold in any state (`carriedGroups`), written after its own groups exactly as the copy held it: the device reads the entry's group id and `me.author`, checks the entry in memory as a restore would (`restorable`, #336), and never keeps, folds into its own state or syncs it. An entry a restore would leave out isn't carried, and of two for one group, only the first that checks out is, so an entry someone else holding the key planted can't keep every restore saying it left one out. A group the device holds goes as it has it, or not at all while it is leaving or a read-only archive (#108). One it uploaded and no longer holds, since it left it, removed it or a dissolve wiped it, stays out. For that the state notes `uploadedGroups`: a tag of each group this device held at a successful upload, never its id. A tag is the unpadded base64url of HKDF-SHA-256 of the backup key under `reconcile/v1/backup-group-tag` ‖ 0x00 ‖ the group id ‖ 0x00 ‖ the member's author (`groupTagFor`, pinned by `src/crypto/vectors/relayBackup.json`), so a group rejoined under a new author on the other device is carried. A tag goes once a read finds the copy without its group, so the device keeps no lasting mark of a group it left; a read that fails keeps every tag. `purgeGroup` sets the relay backup's `checkedDay` back to null in its own transaction, so the next complete pass, the leave's own, takes the group out of the copy, and Erase or a lost phone later that day can't leave it there for the other device to carry. A record from before #327 has no `uploadedGroups`, so on its first upload it takes the copy's groups as its own and carries none, as before. So a restore from the copy brings back every group either device holds, whichever uploaded last, and never one the device that held it left. A copy the device can't read leaves it uploading its own groups, as before #327. A group both devices hold that one of them left (a leave on one device is the member's) comes and goes from the copy as each refreshes, as a deleted Document does, until the other device no longer holds it.
  - **Schedule.** Once a key exists, after the first sync pass of each UTC day by relay time in which every group synced (`createSync`'s `afterPass`), the device reads the relay copy, one GET a refresh day, and uploads if the SHA-256 of the merged plaintext, leaving out each group's `relayNow` and `lastSyncAt`, differs from the last upload's, if the relay holds nothing under the id, or if the relay copy's personal Documents or group ids aren't the merge's, as after a linked device's upload (#247, #327), or it holds a group entry the device couldn't read (#336), so a planted entry leaves the copy at the next refresh. It never uploads on every change, but a purge sets the checked day back (#327), so the pass that purged a group checks again. The relay day is the latest `relayNow` among the device's groups, so a device with no synced group schedules nothing. A failed upload tries again after the next complete pass. Over 16 MiB the device keeps the last good backup. The refresh runs last in the pass, after its key changes (#98) and push upkeep (#99), so it sees each group at the epoch it moved to, and it waits while any group still has a key change due that this device should write, so the relay never holds a copy taken mid-change; `startRelayBackup` waits the same way, leaving its first upload to the next complete pass. With the key the device already keeps, `startRelayBackup` reads and merges the relay copy first, as the refresh does; a new key's id holds nothing yet, so it reads nothing. On a device whose keys are locked with a passkey (#95), the sync loop, and so the refresh, starts only once the passkey unlocks them, and every read or write of the backup key fails while it's locked, so neither the refresh nor `startRelayBackup` can upload or make a key before then.
  - **Status.** Settings shows "Backed up to the relay <day>.", "Your groups will be backed up to the relay the next time Reconcile syncs." before the first upload, or "Your groups are too large for the relay backup. Save a backup file instead.", and nothing while the device keeps no key, unless its last key was retired (#272): "You chose recovery contacts again on another of your devices, so this one stopped backing up to the relay. Link it again from that device to back it up."
  - **Read path.** `fetchRelayBackup(relay, key)` derives the id, GETs and opens the blob, and returns the plaintext, or null for a 404, a failed tag or a bad frame; a relay it can't reach rejects. `importSnapshot(store, plaintext)` checks and keeps it as a restore does, leaving out any group entry that doesn't check out and returning how many (#336). #118 calls both, and keeps the key it recovered with `adoptRelayBackupKey`, with the split of the shares that rebuilt it (#272).
- **Recovery contacts** (#109; [ADR-0043](../../adr/0043-recovery-and-backup.md) §1, [ADR-0008](../../adr/0008-passkeys-and-social-recovery.md), [ADR-0009](../../adr/0009-per-group-identities.md), ADR-0075 §4). People the person trusts hold Shamir shares of the relay backup key, so enough of them together can bring the person back (#118).
  - **Thresholds** (`src/crypto/recoveryPolicy.ts`, no imports). `t` of `n` with 3 ≤ n ≤ 7, 2 ≤ t ≤ 5 and t ≤ n: the 17 pairs from 2 of 3 to 5 of 7. The picker starts at 3 of 5.
  - **Split** (`src/crypto/shares.ts`, the only importer of `shamir-secret-sharing`, pinned at 0.0.4). `splitKey(key, n, t)` makes `n` 33-byte shares (32 y-bytes, then an x-coordinate from 1 to 255) over GF(2^8) reduced by x^8 + x^4 + x^3 + x + 1; any `t` rebuild the key and fewer reveal nothing. `combineShares` rebuilds, or answers null for shares that can't be one set; a wrong key only shows as a backup id the relay doesn't hold.
  - **Box.** Each share is sealed to its contact's `kx` in the group they share (§3, Encryption keys) under info `reconcile/v1/recovery-share`, with UTF-8 group id ‖ contact key ‖ author key as associated data, so a box moved to another group or contact, or posted again under another member's name, never opens. Its plaintext is `{"v":1,"split","t","n","share"}`, `split` being 16 random bytes and `share` the share, both in unpadded base64url. `vectors/shares.json` pins three splits, two shares of a 3-of-5 split that fit either of two keys, and one box, all computed outside the library and @noble.
  - **Choosing** (`chooseContacts`, `src/store/recovery.ts`). The picker offers each current member of each group that goes on for the device (genesis back, not dissolved, read-only or leaving, and this membership still in it) where `can(state, me, 'see-roster')` holds and the member has a `kx`, never the person, by their `displayName` there. Save awaits `startRelayBackup({newKey: true, split})` with a fresh split id, always (#272): whatever key the device held, its own earlier choice's, one recovered with contacts (#118), or one a backup file (#78) or a link (#96) brought, which other copies of the file or the other device hold too. It splits the key, queues one `recovery-share` per contact in that contact's group, keeps the plan and runs a sync pass. When it replaced a key, it then PUTs 65,536 random bytes to the old id, so every older share rebuilds only a key whose backup is gone.
  - **Keeping it gone** (#272). The plan's `retired` list keeps every id a choice on this device replaced. `afterSyncPass`, after the relay backup's refresh, reads each once a relay day, by the latest `relayNow` among the device's groups: a backup there again, as another device's upload that landed just after the overwrite, or nothing, as once the relay forgets an id 180 days after its last write, gets 65,536 fresh random bytes; random bytes already there stay. It notes the day (`retiredCheckedDay`) once every id checked out, so an id the relay couldn't read or take is tried again after the next complete pass. Any other device that still holds a replaced key finds those bytes before its next upload and stops (Relay backup, above), so one person's latest choice wins on every device.
  - **The plan** (`RecoveryPlan`: split, t, n, each contact's group, key, name and group name, when, `retired`, `retiredCheckedDay`, and `supersededAt` once a later choice on another device retired its key, #272) is one record in the store's `device` object store, under its own key, so the store version stays. No backup file, link bundle or relay copy carries it; only its split id goes beside the backup key in a file or a link bundle (#272).
  - **Holding** (`heldShares`, `openHeldShare`). Each device tries every `recovery-share` in each group that goes on for it against its own `kxKey`, and keeps the latest that opens per (group, person) while that person is still a member. It shows only "You're holding a recovery share for <name> (<group>)", in Settings and once on that group's home. A dropped contact still sees their old line, which no longer opens anything; revocable shares are deferred.
  - **Status** (`recoveryStatus`). A superseded plan shows only "You chose recovery contacts again on another of your devices. The people you chose here no longer hold a working share." and Choose again (#272); a device with no plan that holds a key with a split shows "You chose recovery contacts on another of your devices. Who they are stays on that device. Choosing again here replaces them." and Choose again (#272). Otherwise Settings shows "<n> recovery contacts · <t> needed" and each contact's name and group, "No longer in a shared group" for one who left or whose group the person left or saw dissolve, and asks the person to choose again once fewer than `t` are left.
  - **Under passkey unlock** (#95). Both read the device's keys, so both wait behind the unlock screen: on a locked device the backup key and each group's `kxKey` sit in the vault, and reading them fails with `VaultLocked`. The plan holds no key, so it stays out of the vault, in its own device-store record.
- **Recovering with contacts** (#118; [ADR-0043](../../adr/0043-recovery-and-backup.md) §2, [ADR-0008](../../adr/0008-passkeys-and-social-recovery.md), ADR-0075 §4). Someone who has lost every device gets all their groups back through the contacts who hold their shares, after a fixed 72-hour wait that any of their own devices can cancel. Contacts who collude can skip it (an accepted pilot risk, ADR-0075 §4); the wait stops someone passing themselves off as the person to honest contacts.
  - **The code** (`src/crypto/recovery.ts`, pinned by `vectors/recovery.json`, computed outside @noble). Start's Recover with my contacts (`#/recover`, after first run) makes a 16-byte seed `r` and an X25519 key `E_R`, keeps both in the store's `device` object store (`recover-request`; on a device with a passkey vault, which a new device may make at the offer after the pilot notice or during the wait, both go into the vault through `keepKeys` and the record keeps only when it started, #95), and shows `RR1.` + the unpadded base64url of `r ‖ E_R`, with Share the code (`shareOrCopy`, beside fixed words and the app's address), and the check: `u32be(SHA-256("reconcile/v1/recovery-check" ‖ 0x00 ‖ code)[0..4]) mod 10^6` as six digits (`sixDigits.ts`), and the second number (#398): `u32be(HKDF(E_R's secret key, empty salt, "reconcile/v1/recovery-number", 32)[0..4]) mod 10^6` as six digits, which the code doesn't carry, so only this device can show it. Both sit in the linking number's card as "First number" and "Second number", under "Send this code to your recovery contacts, then call them and read them both numbers." The same request, and so the same second number, comes back after a restart until the person confirms a backup or Stop recovering forgets it.
  - **The request mailbox.** Its id is the unpadded base64url of `HKDF(r, empty salt, "reconcile/v1/recovery-mailbox", 32)`, and its blobs are sealed (§3, Seal) under `HKDF(r, empty salt, "reconcile/v1/recovery-seal", 32)`. While its screen is open the new device reads it every 2 seconds from seq 0.
  - **Approving** (`src/recovery/holder.ts`). Settings › Help someone recover (`#/help-recover`, on a device that holds a share) takes the pasted code, asks "Which person?" from the shares held, says "Call <name> or meet them. Make sure it's really them.", and approves only when the first number typed matches the code's check and the second is six digits (spaces aside, #398). It then queues, in one store change with a hold kept on the group's record (`recoveryHolds`: the alert's id, the person, the split approved, a tag, the code, the second number), a `recovery-alert {box}` in the share's group: `box = sealTo(person.kx, {"v":1,"split","tag"}, "reconcile/v1/recovery-alert", UTF-8 group id ‖ person's key)`, where `tag` is 16 random bytes. It goes out with `wake=1` (§6, #99), and the screen says "Holding <name>'s share until <date>. Open Reconcile after then to send it."
  - **Waiting and release.** The hold ends at the alert's relay `received` + 4,320 minutes, by the group's `relayNow`. After each complete sync pass (`afterEveryPass`, before the relay backup's refresh), each open hold stops if the group's log holds a `recovery-cancel` naming its tag from the share's owner key (from anyone else it counts for nothing), or if the share this device now holds for them comes from another split (they chose again); otherwise, once its time has come, the device builds `sealTo(E_R, {"v":2,"split","t","n","share","number"}, "reconcile/v1/recovery-release", UTF-8 request mailbox id)`, `number` being the second number typed (#398), seals it under the request mailbox's key, so it is one 1,024-byte blob, and PUTs it with `ttl_days=7`. A pass that fails runs none of this; a PUT that fails is tried after the next complete pass. A stopped hold drops its code and second number at once. A sent one keeps them while the relay keeps the release, until the group's `relayNow` reaches the hold's end + 7 days, or a cancel arrives; until then Help someone recover names the number it went with ("<name>'s share went to their new device with the second number 966 043.") and offers Send it again with another number (`resendRelease`), which puts a second release with the corrected number and keeps that number on the hold.
  - **The alert and cancel** (`src/recovery/alert.ts`). Any device holding the person's key in that group (a restored or linked one included) opens the alert, and Start and every group home show, until the hold ends: "Someone asked your recovery contacts to restore your Reconcile on a new device. If this wasn't you, cancel now. It completes <date>." with Cancel this recovery, which queues a `recovery-cancel {alert: tag}` per pending alert in its group. The cancel names the alert by its sealed tag, never its event id, so no other member can tell which alert, or which contact, it answers. Every device of the person's then reads the alert as cancelled.
  - **Combine and restore** (`src/recovery/request.ts`). A release that isn't `"v":2`, or whose `number` isn't this request's second number, is left out before any combine (#398): one with another number is counted, and the screen says "A share came with a different second number, so it was left out…", so someone who holds only the code can't use up the tries or have a backup of their own opened. Shares are grouped by split and threshold; only one split's are ever combined. Once a split has `t`, each `t`-subset is tried in the order the shares came, at most 35 in all, and a subset counts only once `fetchRelayBackup` opens the backup its key names. Nothing is written yet: the screen asks "Are these your groups?" over the name of each plain group in that backup, in `<bdi>`, with Yes, restore them (primary) and No, they aren't mine (secondary), in place of the code (#398). No forgets that backup, never opens its id again in this session, keeps the request, says "Nothing was restored. Someone else may have your recovery code. Stop recovering, start again for a new code, and call each contact as you send it.", and keeps waiting, so the real contacts' shares can still complete it. Only on Yes is anything written: `importSnapshot` from the relay (no group is marked as in a backup file), which leaves out a group entry that doesn't check out and counts it in the `restored` step, as a file's restore does (#336), `adoptRelayBackupKey`, and a `recovered` mark in place of the request. The app syncs and opens the picker, which, with Settings, asks the person to choose again; that first choice on a recovered device makes a new key and overwrites the one the contacts held (`chooseContacts`).
- **Second device** (#96; [ADR-0044](../../adr/0044-qr-device-linking.md) as cut by ADR-0074: no device list and no revocation). The existing device (A) shows a code, the new device (B) scans or pastes it, both show a six-digit number, and only A confirms. Then B holds the same groups, keys and logs, so the fold sees one voter and the later ballot counts. B posts no `join`, so it takes no place in the bootstrap (#101), and a vouch from each of one person's devices is one vouch. `src/crypto/link.ts` and `src/crypto/sixDigits.ts` hold the derivations, pinned by `src/crypto/vectors/link.json` (computed outside @noble, one number with a leading zero), and `src/link/session.ts` and `src/link/bundle.ts` hold both sides over the relay.
  - **The code.** Link a new device makes a 32-byte seed `s` and a one-time X25519 keypair `e_A`. The code is `RL1.` and the unpadded base64url of `s ‖ SHA-256(E_A)`: a commitment to `E_A`, not the key, so whoever sees the code can't work out the number before B has posted its key. It's shown as a QR code (an inline SVG) with the same text beside it, and it never appears in a route or a URL. A drops it after 10 minutes, or when its screen closes. `parseLinkCode` trims the text and refuses any other prefix, length, alphabet, padding, or a final character with spare bits set.
  - **The handshake.** Both messages go to the pairing mailbox, the unpadded base64url of `HKDF(s, empty salt, "reconcile/v1/link-mailbox", 32)`, sealed by `Seal` under `HKDF(s, empty salt, "reconcile/v1/link-seal", 32)`. Each is a 1-byte tag (`0x01` from B, `0x02` from A) and a 32-byte key. B posts a fresh `E_B`. A takes the first `E_B` in relay order that it can use, skips blobs that don't open and keys of the wrong length or of low order, ignores every later one, and only then posts `E_A`, once. B takes the first `E_A` in relay order and stops with "That code didn't match. Start again on your other device." unless its SHA-256 is the commitment.
  - **The number and K.** Both compute `ikm = X25519(e, E_other)` (@noble refuses a low-order key, whose result would be all zeros) and `T = "reconcile/v1/link" ‖ s ‖ E_A ‖ E_B`. The number is `u32be(HKDF(ikm, SHA-256(T), "reconcile/v1/link-number", 4)) mod 10^6`, zero-padded to six digits, and `K = HKDF(ikm, SHA-256(T), "reconcile/v1/link-key", 32)`.
  - **Confirm on A only.** B shows the number with "Check that your other device shows the same number, then confirm there." and offers only Cancel. A asks "Does your new device show the same number?" with Match and Don't match, and nothing goes under K before Match.
  - **The bundle.** On Match, A seals a snapshot's plaintext (`takeSnapshot(store, 'link')`: the backup file's JSON without its passphrase layer or any share by link, below) under K: a header blob `{chunks, sha256}`, then the chunks of at most 65,492 bytes, in the bundle mailbox, the unpadded base64url of `HKDF(K, empty salt, "reconcile/v1/link-bundle", 32)`. B skips blobs that don't open, waits until every chunk is there, checks the hash, then `importSnapshot` checks every group as a restore does and keeps them in one transaction as from a link: a group new to B has no backup mark, and one already there keeps its own. B says "Linked. This device now has <n> groups." and syncs. A group entry that doesn't check out is left out, as from a file, and B adds "One group from your other device couldn't be read and was left out." (or "<n> groups … were left out.", #336).
  - **What travels.** Exactly what a backup file holds, less each personal Document's share by link (#105), and nothing else it leaves out. Format 2's keys and epochs (#98): B lands at each group's current epoch with A's secret and encryption key, opens the wraps of later key changes as A does, and posts no `kx`, since it is the same member and the fold already holds that member's key. Only if A's own `kx` (a member from before #98) hadn't reached the relay when it linked does B post one, carrying the same key, and only the first counts. Every personal Document (#93), merged by id as a restore merges it. Not a dissolved group's read-only copy (#108), which stays on A, nor a copy A restored that hasn't heard from its group (#231), and not A's push registration or posted nudges (#99): an endpoint belongs to one device, so B starts with push off and turns it on with its own switch. The relay backup key (#97) travels too, with its split (#272), and B keeps them only if it holds no key, as a restore does, so B keeps the relay backup fresh until a later choice of contacts on A retires the key, when B stops (Relay backup, above). A and B then refresh one relay copy, which merges the personal Documents each keeps, and carries a group only one of them joined after the link (Relay backup, above, #247, #327). Not a personal Document's share by link (#105, `withoutShares`): a share belongs to the device that made it, since personal Documents don't sync and two devices posting one share would roll its link back and forth. So B gets every Document unshared, posts nothing for A's links and can make links of its own, and A keeps each share and alone can stop it. B drops any share a bundle holds as well, so it keeps a share of its own on a Document the bundle replaces (`restoredCopy`) and never takes up A's.
  - **Ending.** Each side zeroes its seed, one-time secret key and K when it closes: after the bundle, on Don't match or Cancel, when the screen closes, when a send fails, and 10 minutes after the code (A) or after posting `E_B` (B). A poll while one is on its way shares its answer, so a screen can't take two keys or post `E_A` twice.
- **Passkey unlock** (#95; [ADR-0008](../../adr/0008-passkeys-and-social-recovery.md), [ADR-0030](../../adr/0030-device-key-fallback.md), [ADR-0042](../../adr/0042-broad-device-support.md)). Offered once after the pilot notice and always in Settings, in two taps, since iOS allows one WebAuthn call per tap. Only `src/platform/webauthn.ts` calls `navigator.credentials`.
  - Tap 1 is `create()` with `rp: {id: location.hostname, name: 'Reconcile'}`, a random 32-byte user id named "Reconcile key", algorithms −8, −7 and −257, `residentKey: 'preferred'`, `userVerification: 'required'`, `attestation: 'none'` and `extensions: {prf: {}}`. Any PRF answer it gives is ignored. Tap 2 is `get()` for that one credential, with user verification required and PRF evaluated on a random 32-byte salt.
  - That answer decides, once: the keys are sealed only when `prf.results.first` is exactly 32 bytes, the authenticator data's UV flag (0x04) is set, and `prfTrusted` holds (`src/platform/prfPolicy.ts`: false on iOS and iPadOS 18.0–18.3, read from `OS 18_x`, or from `Version/` on an iPad that reports a Mac, and false on an Apple touch device whose version can't be read). Then the vault key is HKDF-SHA-256 of the PRF output, salted with the PRF salt, under `reconcile/v1/key-vault`, and the vault is XChaCha20-Poly1305 under it, a random 24-byte nonce first, with `reconcile/v1/key-vault` ‖ the credential id as associated data (`src/crypto/keyVault.ts`, pinned by `src/crypto/vectors/keyVault.json`, computed outside @noble). Otherwise nothing is sealed: "This device's passkey can't protect your keys, so they stay on this device as before." The PRF output is zeroed either way.
  - Store version 6 adds the `vault` object store after #97's version 5, one version at a time (3 → 4 → 5 → 6), and keeps version 4's groups and personal Documents (#93), which hold no key, and version 5's relay backup state. Sealing moves every secret on the device (today each group's current secret, signing key and encryption key, #98, the relay backup key, #97, each shared Document's share keys, #255, each sent application's reply keys, #265, and a recovering device's request seed and secret key, #118) into the one vault record, and deletes the plain copies in the same transaction: the relay backup's record keeps its state without its key. After that, every write of key material (Create group, Join, a backup's or a link's import, a new epoch's secret or encryption key, Leave, Remove, and the relay backup key set, adopted or updated) goes through the store's one write path, `keepKeys`, which reseals the vault with the session's key and refuses while it's locked; every read of the relay backup's state opens the vault too. A record that keeps secrets beside what it says seals them through one mechanism (`src/store/sealing.ts`): the vault's format 2 holds each such record's secrets by its store and id, and the record keeps the rest, with no new format for a new kind. A shared personal Document's seed, signing key and public key (#105) go there, and its record keeps the share's `n`, `lastPostedAt` and `pending` (#255); so do a sent front-door application's reply seed, reply key and invite seed, and its record keeps its door, the group's name and when it was sent (#265), and a recovering device's request seed and X25519 secret key, and its record keeps when it started (#118). Sealing moves them with the rest; on a device sealed before this, they move at its first unlock, and a format 1 vault opens and is written back as format 2. Reading a shared Document or a sent application whole opens the vault, so a locked device refuses it, and so do Share link, Stop sharing, a share's posts and every write of either; Personal and the editor read each Document's words and whether it's shared with no key, and the editor still saves while locked, marking the share pending and writing no key. Its launch posts (`keepSharesAlive`) run only once the keys are unlocked, after the sync loop starts. A store opened on a sealed device reads nothing until the passkey's key unlocks it; the key then stays in memory for the session. `Store.requireUnlocked()` is the one check before anything hands keys on: Save a backup calls it, and so does Link a new device (#96), before it shows a code and again before it sends the bundle; a tab whose keys another tab locked shows "Your keys on this device are locked with your passkey. Close Reconcile, open it again and unlock it, then link a new device." instead of a code. A link into a device with a vault writes through `keepKeys`, so what arrives is sealed. Restore on the unlock screen drops the relay backup's state with the vault, and keeps the file's key, if any. It forgets each sent application whose reply keys went with the vault, and a recovery request whose keys did (#118), and gives each shared Document whose keys went with it the file's share of that Document, marked pending and paused (#328: nothing says it's the share the vault held, and it may have been stopped since), or none, before the file's Documents merge. Erase never needs it.
  - **Failing closed** (#390, #391).
    - The vault seals only keys it reads back. `encodeVaultKeys` decodes its own plaintext and refuses (`UnsealableKeys`) a key that isn't 32 bytes, a secret outside 1 to 64 bytes, a record with no secret, or a name it doesn't take. The write then aborts and the vault stays as it was, since one bad entry would stop the whole vault opening. `sealKeys` refuses a passkey with no credential id or a salt that isn't 32 bytes.
    - With a vault, `keepKeys` refuses a record that holds only some of its keys, rather than write them in the clear.
    - `keepKeys` plans every write, then deletes, reseals the vault, and puts, in that order. So a transaction that commits early, as an await of anything but IndexedDB inside it would make it, leaves every key in its record or in the vault. `sealKeys` writes the new vault once, already holding every key.
    - Store version 8 changes no store. It marks the vault's format 2, and each later format bumps the version too, so a build from before it can't open the database at all, rather than read the vault as one that doesn't open and offer Restore, which clears it. Telling the person to update the app in that case is deferred.
    - Zeroing is best effort: each plaintext's bytes, the keys an unlock opens only to check, and the session's key once Restore replaces the vault. JSON strings, and keys handed to callers, can't be zeroed.
    - What a locked device still holds in the clear is listed in the [threat model](../../plan/12_Security_Privacy_Threat_Model.md).
  - Nothing about passkeys reaches the relay: the password manager sees the app's host, "Reconcile" and "Reconcile key".
- **Library rule.** Audited libraries only: `@noble/curves`, `@noble/hashes` and `@noble/ciphers`, plus `shamir-secret-sharing` for recovery shares (ADR-0075 §4). **No hand-rolled cryptography.** Randomness comes only from `randomBytes` or `crypto.getRandomValues`. The one other library that touches a secret is `qr` (#96), which draws and reads the linking code and does no cryptography; only `src/app/qr.ts` imports it.

Restored (§11): recovery contacts (#109, #118). Passkey unlock (#95), a second device by scanning a code (#96) and the relay backup (#97) are above. Per-member encryption keys and a new group key on leave (#98) are above and in §4; removal (#115) ends a membership too, with `remove`, so it changes the key the same way.
