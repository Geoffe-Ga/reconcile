### Encryption keys and a new group key

#98 builds them in `client/src/crypto/box.ts`, `client/src/crypto/epoch.ts`, the fold, and `client/src/store/epochs.ts` and `sync.ts` ([ADR-0009](../../../adr/0009-per-group-identities.md), [ADR-0072](../../../adr/0072-protocol-details-for-decomposition.md) item 11, ADR-0073, ADR-0074). When a membership ends, the group gets a new secret that only the members who remain can open, and moves to the mailbox it derives. #224 lets the group recover from a key change whose wraps don't open (`client/src/engine/keyChecks.ts`; [ADR-0075](../../../adr/0075-safeguards-for-the-revised-mvp.md)'s 2026-11-11 amendment).

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `kx` | `{kx}`: the author's X25519 public key, 32 bytes in canonical base64url | the author is a member with no `kx` yet: the first per member counts, and one their `genesis` or `join` carried came first. A key of low order (one of the five @noble refuses) counts as none, at genesis, join or here, so nobody can post a key no box can be sealed to and stop the key from ever changing | #98 |
| `key-rotate` | `{epoch, commit, wraps}`: the next epoch (a u32 from 1), its commit, and one wrap per member key | a current member wrote it, and no key change of theirs was refused (#224); an event for which `endsMembership` holds (`leave`, or `remove`, #115) has applied since the last canonical key change, or genesis; `epoch` is the fold's `nextEpoch`, one past the last key change's, canonical or refused; and the wraps' keys are **exactly** the current members that have a `kx`. The first valid one per epoch is canonical (relay order decides, ADR-0073), unless it is refused (below) | #98, #224 |
| `unwrap-failed` | `{rotation}`: a key change's event id | read ahead, it refuses that key change when its author is one of the key change's recipients, no removal had passed against them by the key change's place (#372), and it was read from the mailbox the key change moves the group out of, and no `key-taken` keeps it (below). Where it sits, it counts when it names a refused key change and its author is a recipient. A suspension doesn't hold it back | #224 |
| `key-taken` | `{rotation}`: a key change's event id | read ahead, it keeps that key change from being refused when its author is one of its recipients, no removal had passed against them by the key change's place (#372), and it was read from the key change's own epoch's mailbox. Where it sits, it counts when it names the canonical key change and its author is a recipient. A suspension doesn't hold it back | #224 |

- **Commit and wraps** (`epoch.ts`). `commit` is the base64url SHA-256 of UTF-8 `reconcile/v1/epoch-commit` ‖ `0x00` ‖ the group id's UTF-8 ‖ u32be(epoch) ‖ the 32-byte secret. Each wrap is a box (§3) of the secret sealed to the member's `kx` under info `reconcile/v1/epoch-wrap`, with the group id ‖ u32be(epoch) ‖ the member's key ‖ the commit as associated data, each text in UTF-8 as the event spells it, with nothing between them, so a wrap moved to another member, epoch or group never opens. A wrap that opens to a secret that doesn't match the commit counts as missing. Since #224 a wrap's ephemeral key and nonce are made from the secret, not drawn fresh: the first 32 and last 24 of the 56 bytes of HKDF-SHA-256(ikm = secret, empty salt, info = UTF-8 `reconcile/v1/epoch-wrap-coins` ‖ `0x00` ‖ the member's 32-byte `kx` ‖ the associated data). So whoever holds the secret makes every wrap again, byte for byte (`wrapsHold`). `src/crypto/vectors/epoch.json` pins the commit, the associated data, a #98 wrap and one made so, all computed outside @noble.
- **Epochs.** Each canonical key change moves the group to its epoch. A refused one moves nothing and spends its epoch number, so the next names the one after it and epochs can skip; no refused epoch's mailbox ever reaches an honest device's log. A record read from any week's mailbox of epoch e after e's key change changes nothing (§4, The fold), so a stale invite's join and a late writer's event are ignored there, a `leave` included (Stranded leaves, below). Relay seqs are global, so a device's log holds records of several mailboxes, merged by seq (§7, Each pass); invite chunks and the backup carry each record's epoch.
- **The duty** (`sync.ts`). After a pass in which every group synced, a device whose member is current, holds the current epoch's secret, isn't leaving, wrote no refused key change (#224) and has no removal passed against them (#115; #372), and that sees a key change due, syncs that group once more. If one is still due, it makes a fresh secret, wraps it to every current member with a `kx` (itself included), wipes it, and posts the signed `key-rotate`, naming the fold's `nextEpoch`, straight to the outgoing epoch's mailbox for the week its relay minute falls in (#110). It learns the new secret as every other device does, from its own wrap. Devices that race each post one; the fold keeps the first.
- **The freeze.** While a key change is due, or the fold has one this device hasn't taken up, the outbox sends only `key-rotate`, `leave`, `unwrap-failed` and `key-taken`, and everything else waits in its place.
- **The check** (#224, `epochs.ts`). Before it takes a key change up, a device opens its own wrap and makes every other wrap again from the secret; it takes the key up only when every wrap matches. When its own wrap doesn't open, or any wrap isn't the secret's, it queues an `unwrap-failed` naming the key change, once, which the next pass posts to the old epoch's mailbox. A device whose own `kx` isn't the one the fold holds for it, or that has no wrap, can't judge and says nothing.
- **Refused** (#224, `keyChecks.ts`). The fold refuses a key change when an `unwrap-failed` from one of its recipients names it, read from the mailbox it moves the group out of, and no `key-taken` from one of its recipients names it, read from its own epoch's mailbox. It reads both ahead, before it starts, and decides at the key change's place, so the records between them in the old mailbox fold as usual. Neither counts from a recipient a removal had passed against by then (#372): nothing else of theirs counts (#115), a key change wraps to them until a `remove` lands, and every other recipient's device checks their wrap anyway. Who that is comes from the records before the key change, so devices that hold the same log agree. A refused key change moves nothing, spends its epoch, bars its author from writing another and leaves one due; `refused` lists them. A device that takes up a key change the fold refused, because every wrap checks out here, as after a false `unwrap-failed`, posts a `key-taken` naming it to the new epoch's mailbox first, so its own fold, and every fold that reads it, keeps it. A device reads a new epoch's mailbox only once it has checked every wrap, so a `key-taken` for a key change nobody honest took up never reaches an honest device.
- **The switch.** A pull that brings a key change past the device's epoch, canonical or refused, that checks out here moves the group, in the same store change (the first in relay order; a refused one that doesn't check out is passed over): the new secret and epoch, a base cursor at the key change's seq for the new epoch's mailboxes (they hold nothing earlier) with no cursor of the old epoch's, and this member's own records that landed in any of the old epoch's mailboxes after the key change, then every stranded leave (below), each once, put first in the outbox to post again, once the entries the pass posted have left it, so each goes once. An invite's adoption posts the same. The device reads the new epoch's mailboxes at once and stops reading the old ones; GET is ascending, so everything before the key change is already in. A later key change in the new mailbox moves it again in the same pass.
- **No wrap.** A device with no wrap that opens stays where it is. Group home says "You left this group on another device." when this membership has left, and otherwise "This group's key changed and this device didn't get the new one. Ask someone in the group for a new invite link.", and offers no invite link. A newer invite's merge (§7) brings the current secret, once it matches its key change's commit, and the frozen outbox goes to the new mailbox.
- **Stranded leaves and removes** (#225, #376). A member who hadn't heard of a key change posts their `leave` to the old epoch's mailbox, after it, or a `remove` (#115) there that takes out the member a removal names. The fold ignores it there, as it does any record of another epoch's mailbox, and a device that took the key up before it landed never reads it, so honouring it there, at its own place or at the key change's, would leave devices folding different states. Instead it has to reach the new epoch's mailbox, as #98's late writers' records do, and it ends the membership where it lands there, on every device alike; the next key change, then due, must leave the leaver, or the person removed, out (`wraps` exactly the current key holders). A `remove` lands as any does: the fold takes it there only once the removal's pass is final, from a member who may remove, while the person it names is still in the group. Two devices take a leave there, and any device that read a remove:
  - **The leaver's own.** A leaving device reads its mailboxes once more after the relay takes its leave (§7, Leave). When that read brings a key change that came before the leave and checks out here, the device moves, posts the leave again in the new epoch's mailbox and lets the group go once the relay takes it there. Otherwise it lets the group go at once, saying nothing of a key change that doesn't check out.
  - **Any that read it.** The fold lists each `leave` and `remove` read from an earlier epoch's mailbox after the key change out of it, admitted where it sits and from someone still a member, in `stranded`, each event once, with `member`, the person it takes out: the leaver, or the person the removal names. It drops one once its author or that member is no longer a member, since its copy would change nothing then. A device that moves, by sync or an invite's adoption, posts each one again, signed as it is, to the new epoch's mailbox. That covers a leaver whose device was lost before it could, or who held no `kx` and so had no wrap, and a remover whose device is gone (#376). A remover's own device that moves posts its late `remove` again anyway, as it does any of its late records, and any member's device that folds the final pass posts a `remove` of its own (§7, Removal), so a carried copy is the original, which every device then folds at one place.

  The leaver held a wrap in the key change their leave missed, as any member then did, so nothing more is exposed; the next key change excludes them. A copy posted twice folds once, at the first. A leaver whose device is gone, and whose leave no device read, still stays listed: that is accepted for the pilot. Golden vectors: `vectors/epoch-stranded.json` and `vectors/epoch-stranded-remove.json`; `src/store/strandedLeave.test.ts` plays both leave cases and a carried remove on the fake relay.
- **Who it covers.** Everyone in the group is a member for this, at any level and before their voting rights arrive (#101), so all of them get a wrap.
- **Size** (#226). A `key-rotate` record is 335 bytes plus 188 per wrap. The 335 are the 96-byte record header and the event's JSON around the wraps, with a 13-digit `ts` and a one-digit epoch. The 188 are each wrap's `"member":"wrap",`: a 43-character key and a 104-byte box (§3: a 32-byte ephemeral key, a 24-byte nonce, the 32-byte secret and a 16-byte tag) in 139 base64url characters. So 338 members with a `kx` fit the 64,000-byte largest record (§2), and the 339th passes it, at any epoch. Nothing checks this, since the duty seals the record straight into a blob. Up to 346 members, the key change still posts, but no backup file or link bundle that holds it restores, because a restore (§3) refuses any record over 64,000 bytes. From 347, the seal's 65,492 bytes refuse it, so the key can't change and the freeze holds the outbox until enough members leave. Pilot groups are far smaller. If groups ever get that big, the key change needs chunking: its wraps split across several records, as an invite splits its log into chunks (§7).
- **After a dissolve** (#108). The fold ignores every event after a `dissolve`, a `leave` and a `key-rotate` included, so no key change becomes due or lands after it, and the dissolve itself clears `rotationDue`, even when a leave folded just before it with no key change yet. A dissolved group's devices archive it, so none takes the duty, posts a `kx` or holds an outbox frozen: the outbox is gone, and the loop sends and reads nothing for it (§7, Dissolve). A dissolved group's home shows its archive note, never a no-wrap line. Golden vectors: `vectors/dissolve-rotate.json`.
- Golden vectors: `vectors/rotate-*.json` and `vectors/epoch-*.json` (#224: refused, recovers, honest, race; #225 and #376: stranded), the fast-check properties that a record read from another epoch's mailbox, anywhere, changes nothing, and that a stranded leave's copy in the new mailbox folds the same with or without the old copy, and `keyChecks.test.ts`'s that a key change is refused exactly when a recipient's `unwrap-failed` from its old mailbox names it and no recipient's `key-taken` from its new one does. `src/store/poisonedKeyChange.test.ts` plays a member who posts a key change that doesn't open, one that opens for some only, and a false `unwrap-failed`, on the fake relay. Deferred past the MVP (#98): MLS, key-grant events, re-sending a key change (a device away past 30 days uses §7's catch-up line), clearing a leaver's other device, and revoking live invite envelopes.
