# SPEC: The Reconcile MVP

- **Status:** The build contract for the MVP, rewritten for [ADR-0073](../adr/0073-mvp-scope.md), [ADR-0074](../adr/0074-mvp-scope-revised.md) and [ADR-0075](../adr/0075-safeguards-for-the-revised-mvp.md)
- **Date:** 2026-11-09
- **Inputs:** `docs/plan/` (product), ADRs 0001–0075 (`docs/adr/`), and the issues under epics #57–#60 (the foundation) and #82–#88 (the restored features)
- **Earlier version:** the full Phase 1 design of 2026-11-07, at commit `f4b9e2b`. An ADR that cites "spec §N" means that version's numbering.

This spec says **what the MVP builds and how**. It links to ADRs for *why* and doesn't repeat them. When this spec and an ADR disagree, the ADR wins (ADR-0075, then ADR-0074, then ADR-0073). An issue that adds or changes a contract updates this spec in the same PR.

## 1. Goal

Two pilot groups of 5–15 people each use Reconcile for six weeks ([ADR-0056](../adr/0056-pilot-plan.md)). One is an everyday group, such as family or friends. The other is an organizing or community group whose content isn't sensitive. Each group governs its living Documents from its own devices, with no central database:

> **Invite → Join → Read → Propose → Discuss (linked chat) → Vote → Update**

The pilot succeeds when (ADR-0056):

- each group completes the loop at least 3 times;
- at least 70% of members vote at least once;
- nobody loses their keys.

The build succeeds when:

1. **The loop runs on real devices.** Three browser profiles run it in CI through the real relay, one of them offline while it votes (#67). An installed iPhone and a second device run it against the deployed VM (#68). Before the pilot starts, at least 5 testers complete it on at least 3 devices, including an installed iPhone and desktop Chrome (ADR-0056).
2. **The relay learns nothing readable.** An e2e test scans everything the relay stored and logged after a full loop, and finds no group words, names or keys, and no client IP address (#71).
3. **Every device builds the same Document.** The same relay-ordered records fold to the same state on every device (property tests, #63).
4. **The gates pass** (§10).

The MVP has two layers:

- **The foundation** (epics #57–#60) is ADR-0073's simple loop: one level, one Document, and fixed 7-day votes. §3–§9 describe it in full.
- **The restored features** (epics #82–#88) bring back what ADR-0074 lifts, Phase 2 coalitions included, with ADR-0075's safeguards. §11 names the issues that build each one.

Protective features are real but quiet. Nothing in the UI suggests the app is for illegal activity (ADR-0018, [DESIGN.md](../../DESIGN.md)).

## 2. System overview

```
┌──────────── A member's device (installed PWA, TypeScript) ──────────┐
│  UI (React Aria) ──▶ engine: fold, tally, can()                     │
│                         ▲                                           │
│  store (IndexedDB): per-group keys and secret, the relay-ordered    │
│  log, the outbox, the sync cursor, private drafts                   │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │ sealed, padded blobs (1, 4, 16 or 64 KiB)
                         ┌─────────▼─────────┐
                         │  Relay (Python)   │  mailboxes only: each blob
                         │  FastAPI, SQLite  │  with its seq and receipt minute
                         └───────────────────┘
```

| Part | Language | What it is | ADRs |
|---|---|---|---|
| `client/` | TypeScript | The PWA: UI, engine (`src/engine`), crypto (`src/crypto`), store (`src/store`) and network (`src/net`) | 0005, 0022, 0029, 0073 |
| `reconcile/` | Python | The relay only: blind mailboxes on FastAPI and SQLite | 0007, 0019, 0028 |
| `deploy/` | Caddy, systemd, bash | One VM that serves the app and the relay from one origin, deployed by a script the founder runs (#68) | 0041, 0073 |

**One engine.** The TypeScript engine is the only implementation of the governance rules. Golden JSON vectors in `client/src/engine/vectors/`, and the fast-check properties beside them, pin its behavior (ADR-0073). Python runs the relay and nothing else.

**Boundaries,** enforced by `client/plans/architecture/.dependency-cruiser.cjs` and ESLint:

- `src/engine`, `src/crypto` and `src/store` import no React or UI code, and `src/engine` imports nothing from `src/net` (#63).
- Only `src/net/` calls `fetch`, `XMLHttpRequest`, `WebSocket` or `EventSource` (#64). The service worker lives there too (`src/net/serviceWorker.ts`, #76).
- Only `src/crypto` imports `@noble/*`, and `src/crypto` imports no other third-party package (#69) except `shamir-secret-sharing`, which only `src/crypto/shares.ts` imports (ADR-0075 §4).
- Every visible string comes from one typed messages module, `client/src/app/messages.ts` ([ADR-0055](../adr/0055-accessibility-and-languages.md) as cut by ADR-0073, #65).

## 3. Identity and keys

[ADR-0009](../adr/0009-per-group-identities.md), as ADR-0073 cut it: every membership has its own random keys, with no root identity behind them.

- **Signing keys** (#69). Create group and Join each make a fresh Ed25519 keypair, stored with that group's records only. An event's `author` is the public key in unpadded base64url (43 characters). The secret key stays in the store: the actions read it there to sign, and no screen is handed it. Store version 2 brought these keys in and deleted the stub era's unsigned data on upgrade, with no migration.
- **Records** (#69). A record is `publicKey (32 bytes) ‖ signature (64) ‖ event bytes`. The signature covers UTF-8 `reconcile/v1/event` ‖ `0x00` ‖ event bytes. `sign(ctx, secretKey, msg)` and `verify(ctx, publicKey, sig, msg)` in `src/crypto/sign.ts` take the tag as a typed parameter, and an invite token signs under its own tag, `reconcile/v1/invite-token` (#73). Verification calls `ed25519.verify(sig, msg, pub, { zip215: false })`, never the library default, which accepts non-canonical encodings and small-order keys. The outbox and the log hold records, and a record's verdict is kept per page load by the SHA-256 of its bytes, so a re-fold doesn't verify it again.
- **Group secret** (#71). Genesis makes 32 random bytes that only members hold. The group's other values derive from it with HKDF-SHA-256, an empty salt and 32 bytes of output (`src/crypto/groupKeys.ts`, pinned by `src/crypto/vectors/derive.json`):
  - each relay week's mailbox id (#110), in unpadded base64url, with info UTF-8 `reconcile/v1/mailbox-week` ‖ `0x00` ‖ the week as 4 big-endian bytes (`deriveWeekMailboxId`). The week of relay minute `m` is ⌊m / 10,080⌋ (`weekOf`), so weeks turn over on Thursday at 00:00 UTC, and it comes from the relay's `now` only, never the device clock. It replaced M2-02's one id per secret (info `reconcile/v1/mailbox`) for all group traffic; an invite's mailbox is its own;
  - the seal key, with info `reconcile/v1/seal-key`, the same in every week of the secret's epoch. The mailbox id stays a blob's associated data (Seal, below), so a blob can't be moved to another week.

  The store keeps only the secret, at store version 3, and derives the rest where it's needed. Version 3 deleted older data, whose relay blobs anyone could read, on upgrade, with no migration.
- **Encryption keys** (#98; ADR-0009, ADR-0074). Create group and Join also make a random X25519 keypair for that one group (`src/crypto/box.ts`), kept in the group's record beside its signing key (`kxKey`) and in the backup file. `genesis` and `join` carry its public half as `kx`, in unpadded base64url, and the fold records it on the member. A device whose member has no `kx`, as one that joined before #98, posts `kx` once. A **box** seals a plaintext to one X25519 public key: a fresh ephemeral key, `dh = X25519(ephemeral, public key)` (a low-order key, whose `dh` would be all zeros, is refused), `k = HKDF-SHA-256(dh, salt = ephPub ‖ public key, info, 32)`, and `ephPub (32) ‖ nonce (24) ‖ XChaCha20-Poly1305(k, nonce, aad)(plaintext)`; `openBox` returns null for every failure alike (pinned by `src/crypto/vectors/box.json`, sealed outside @noble and opened again by libsodium). #109's recovery shares reuse it. The group's secret has an **epoch**, 0 from genesis, and each new one is committed to and wrapped as §4 says (`src/crypto/epoch.ts`, pinned by `vectors/epoch.json`). A group kept before #98 reads as epoch 0, so the store version stays 3.
- **Seal** (#64, #71). XChaCha20-Poly1305 (`@noble/ciphers`) under the seal key, with the mailbox id's UTF-8 as associated data. A blob is a random 24-byte nonce, then the ciphertext of (a 4-byte big-endian length ‖ the payload ‖ zeros up to the size less 40), then a 16-byte tag, in the smallest of the four sizes where the payload is at most the size less 44. A payload is at most 65,492 bytes. `open` authenticates first, and returns null alike for a wrong size, key or mailbox, any changed byte, or a length that runs past the frame. A blob that fails to open is skipped, and the cursor still moves past its seq. `createSync` takes the seal as a required option, and the frame-alike stub is a test fixture in `src/test/` that the app can't import (#151).
- **Largest record** (#71). Create group, the composer and a new version (#72) build the real record and refuse it, tied to the field, when it's over 64,000 bytes, counting bytes, not characters. The store refuses one too. The margin below 65,492 lets #73 carry any record, with its seq and receipt time, in one invite chunk.
- **Invite seed** (#73). Copy invite link makes a random 32-byte seed, and the invite mailbox id and key derive from it through the same HKDF, with infos `reconcile/v1/invite-mailbox` and `reconcile/v1/invite-key` (`src/crypto/invite.ts`, pinned by `src/crypto/vectors/invite.json`, computed outside @noble). The link is `${origin}/#join/${seed}`, 43 base64url characters, so the seed never reaches a server, and the group secret travels only inside the sealed envelope (§7). `parseInviteLink(text)` returns the 32-byte seed, or null, for a whole link from any origin or the bare seed, so Start's paste field reads invites the same way. The tracer's `#/join/{payload}` form still routes to Join, where it shows the expired-or-damaged line.
- **Seat proof** (#100; ADR-0009, ADR-0036). A group that reconciles makes a **seat**: an Ed25519 keypair whose secret sits in its reconcile Proposal, so only its sealed log holds it, and whose public key the coalition's genesis names. A participant joins the coalition under a fresh key and name of their own, never their group key, and carries `sign('reconcile/v1/seat', seatSecret, UTF-8 coalition id ‖ 0x00 ‖ joiner's 32-byte public key)` (`src/crypto/seat.ts`, checked against WebCrypto). It shows the group, never the person: anyone holding the seat secret can make one.
- **Share seed** (#105, §11 Share link). Share link makes a random 32-byte seed and a fresh Ed25519 keypair for one personal Document, used for nothing else. The share mailbox id and seal key derive from the seed through the same HKDF, with infos `reconcile/v1/share-mailbox` and `reconcile/v1/share-key` (`src/crypto/share.ts`, pinned by `src/crypto/vectors/share.json`, computed outside @noble), and each copy is signed under its own tag, `reconcile/v1/share`. The link is `${origin}/#share/${seed}.${publicKey}`, so neither reaches a server.
- **Invite token** (#73). `{by, sig}`: the inviter's public key and `sign('reconcile/v1/invite-token', key, UTF-8 group id)`, both base64url, carried in the joiner's `join`. The fold sets the member's `invitedBy` to `by` only when the signature verifies and `by` was a member before the join. A token that is missing, malformed, from a non-member, over another group's id or signed under the event tag names no one and never invalidates the join (`src/engine/vectors/invite.json`, signed outside @noble).
- **Names** (#69; [ADR-0045](../adr/0045-names-in-groups.md) as cut by ADR-0073). A name is fixed at join. When two members' names match after NFC, trimming and lowercasing, each shows ` · ` and the first 4 hex characters of the SHA-256 of its public key. Names render inside `<bdi>`.
- **Backup file** (#78; [ADR-0043](../adr/0043-recovery-and-backup.md) and [ADR-0044](../adr/0044-qr-device-linking.md) as cut by ADR-0073). One passphrase-sealed file holds every group's keys, secret and log, and every personal Document (#93), and nothing is uploaded.
  - The key is scrypt (N = 2^17, r = 8, p = 1, 32 bytes) over the NFC passphrase's UTF-8 and a random 16-byte salt (`src/crypto/backup.ts`). A passphrase has at least 8 characters, counted as graphemes after NFC.
  - The seal is XChaCha20-Poly1305 under a random 24-byte nonce, with the 47-byte header as associated data: `RCB1`, log2 N, r, p, the salt and the nonce. `src/crypto/vectors/backup.json` pins the format with a file sealed outside @noble.
  - `openBackup` refuses another magic, a log2 N above 20 (or r other than 8, or p other than 1) before deriving anything, and a failed tag after, all with one plain error.
  - The plaintext is JSON with bytes in unpadded base64url (`src/store/snapshot.ts`), at format 2 (#98). For each group it holds the secret and its epoch, the signing key, the encryption key, your name and author, the log's event bytes with their seqs, receipt times and, when it isn't 0, the epoch of the mailbox each was read from, the cursor, the last relay `now` and `instance`, the last successful sync time and the missing-history flag. It leaves out the outbox and drafts, so a restore never sends stale intent, a group whose leave waits or whose genesis the relay hasn't returned, and a dissolved group's read-only copy (#108), whose ballots are due to be cleared, or the group to be erased, and which a file would keep past that. Beside `groups`, a `personal` list holds each personal Document whole: `{id, title, text, createdAt, updatedAt}` (#93), plus `share`, `{seed, secretKey, publicKey, n, lastPostedAt, pending}` with bytes in base64url, while it is shared by link (#105, §11), so a restore keeps the same link. The header stays as it was. A format 1 file, as #78 and #93 wrote it, still restores: every record at epoch 0 and no encryption key, which the sync loop then makes. A file of either format without `personal`, as every one before #93, holds no personal Documents.
  - Restoring reads at most 64 MiB, opens the file, and checks everything before it writes anything: every field's shape, that each signing key makes its author, that every record verifies, that each log folds to its own group, that a secret past epoch 0 is the one its epoch's key change commits to (#98), and that each personal Document is one the editor could have saved, each id once. Anything wrong fails as a wrong passphrase does. It writes every group and personal Document in one transaction, and if any write fails, none stays. For a group already on the device, whichever whole copy synced later stays, and one this device is leaving or keeps read-only (#108) stays as it is. A group whose log in the file folds to a `dissolve`, as an older app's file could hold, comes back as a read-only copy that never syncs, so a restore never brings a dissolved group back to life. A personal Document merges by id the same way: the file's replaces the device's only when its `updatedAt` is later, so a tie keeps the device's. A file's copy with no share keeps the device's share, marked pending, so no live link is lost (#105). A restored group keeps the file's last sync time, so an old backup still shows the catch-up line (§7, #73).
  - Restoring it brings the groups back, or sets up a second device that votes as the same person: both hold the same per-group key, so the fold sees one voter, and the later ballot counts.
  - It also carries the device's relay backup key as `backupKey`, when the device keeps one (#97, ADR-0075 §4). A device restored from it keeps that key if it holds none, so it keeps the relay backup fresh; one that holds a key keeps its own. A file without `backupKey` brings no key, and a malformed one fails the restore.
- **Relay backup** (#97; [ADR-0043](../adr/0043-recovery-and-backup.md) §3 as ADR-0074 revised it: a random backup key replaces the root key). An encrypted copy of every group on the device, kept on the relay so recovery contacts (#118) can bring them back after every device is lost.
  - **Key.** `startRelayBackup(services, {newKey})` (`src/store/relayBackup.ts`) makes a random 32-byte backup key when the device has none or `newKey` is set, keeps it device-wide in the store's `device` object store (store version 5, which adds it and deletes nothing), in no group (on a device whose keys are locked with a passkey, the record keeps its state and the vault its key, #95), uploads at once, and returns the replaced key's id, or null. #109 calls it when someone chooses contacts. No screen makes one before that. The key travels in the backup file, above, and so in #96's link bundle, and never goes to the relay, even sealed.
  - **Id and seal** (`src/crypto/relayBackup.ts`, pinned by `src/crypto/vectors/relayBackup.json`, computed outside @noble). The id is the unpadded base64url of HKDF-SHA-256 of the key under `reconcile/v1/backup-id`, 43 characters; the seal key derives under `reconcile/v1/backup-seal`. A blob is `RCR1` ‖ a random 24-byte nonce ‖ XChaCha20-Poly1305 of (a 4-byte big-endian length ‖ the plaintext ‖ zeros) with its tag, in the smallest of 64 KiB, 256 KiB, 1 MiB, 4 MiB and 16 MiB that holds it, with `RCR1` ‖ the id's UTF-8 as associated data. `openRelayBackup` returns null alike for a wrong size, magic, key, any changed byte or a bad frame.
  - **Plaintext.** The backup file's plaintext without its passphrase layer or `backupKey`: `encodeSnapshot` of `deviceSnapshot`, the one place a snapshot is gathered, with the key taken out. So the relay backup carries whatever a backup file does: format 2's keys and epochs (#98), so a restore from it lands each group at the epoch it held, and every personal Document (#93) with its share by link while it is shared (#105), so a device restored from it keeps the same link and can stop it, but never a dissolved group's read-only copy (#108) or a push registration (#99). A restore from it merges personal Documents as a file's restore does, so a later copy with no share keeps the restoring device's share, marked pending (`restoredCopy`).
  - **Schedule.** Once a key exists, after the first sync pass of each UTC day by relay time in which every group synced (`createSync`'s `afterPass`), the device uploads if the SHA-256 of that plaintext, leaving out each group's `relayNow` and `lastSyncAt`, differs from the last upload's. It never uploads on every change. The relay day is the latest `relayNow` among the device's groups, so a device with no synced group schedules nothing. A failed upload tries again after the next complete pass. Over 16 MiB the device keeps the last good backup. The refresh runs last in the pass, after its key changes (#98) and push upkeep (#99), so it sees each group at the epoch it moved to, and it waits while any group still has a key change due that this device should write, so the relay never holds a copy taken mid-change; `startRelayBackup` waits the same way, leaving its first upload to the next complete pass. On a device whose keys are locked with a passkey (#95), the sync loop, and so the refresh, starts only once the passkey unlocks them, and every read or write of the backup key fails while it's locked, so neither the refresh nor `startRelayBackup` can upload or make a key before then.
  - **Status.** Settings shows "Backed up to the relay <day>.", "Your groups will be backed up to the relay the next time Reconcile syncs." before the first upload, or "Your groups are too large for the relay backup. Save a backup file instead.", and nothing while the device keeps no key.
  - **Read path.** `fetchRelayBackup(relay, key)` derives the id, GETs and opens the blob, and returns the plaintext, or null for a 404, a failed tag or a bad frame; a relay it can't reach rejects. `importSnapshot(store, plaintext)` checks and keeps it as a restore does. #118 calls both, and keeps the key it recovered with `adoptRelayBackupKey`.
- **Second device** (#96; [ADR-0044](../adr/0044-qr-device-linking.md) as cut by ADR-0074: no device list and no revocation). The existing device (A) shows a code, the new device (B) scans or pastes it, both show a six-digit number, and only A confirms. Then B holds the same groups, keys and logs, so the fold sees one voter and the later ballot counts. B posts no `join`, so it takes no place in the bootstrap (#101), and a vouch from each of one person's devices is one vouch. `src/crypto/link.ts` and `src/crypto/sixDigits.ts` hold the derivations, pinned by `src/crypto/vectors/link.json` (computed outside @noble, one number with a leading zero), and `src/link/session.ts` and `src/link/bundle.ts` hold both sides over the relay.
  - **The code.** Link a new device makes a 32-byte seed `s` and a one-time X25519 keypair `e_A`. The code is `RL1.` and the unpadded base64url of `s ‖ SHA-256(E_A)`: a commitment to `E_A`, not the key, so whoever sees the code can't work out the number before B has posted its key. It's shown as a QR code (an inline SVG) with the same text beside it, and it never appears in a route or a URL. A drops it after 10 minutes, or when its screen closes. `parseLinkCode` trims the text and refuses any other prefix, length, alphabet, padding, or a final character with spare bits set.
  - **The handshake.** Both messages go to the pairing mailbox, the unpadded base64url of `HKDF(s, empty salt, "reconcile/v1/link-mailbox", 32)`, sealed by `Seal` under `HKDF(s, empty salt, "reconcile/v1/link-seal", 32)`. Each is a 1-byte tag (`0x01` from B, `0x02` from A) and a 32-byte key. B posts a fresh `E_B`. A takes the first `E_B` in relay order that it can use, skips blobs that don't open and keys of the wrong length or of low order, ignores every later one, and only then posts `E_A`, once. B takes the first `E_A` in relay order and stops with "That code didn't match. Start again on your other device." unless its SHA-256 is the commitment.
  - **The number and K.** Both compute `ikm = X25519(e, E_other)` (@noble refuses a low-order key, whose result would be all zeros) and `T = "reconcile/v1/link" ‖ s ‖ E_A ‖ E_B`. The number is `u32be(HKDF(ikm, SHA-256(T), "reconcile/v1/link-number", 4)) mod 10^6`, zero-padded to six digits, and `K = HKDF(ikm, SHA-256(T), "reconcile/v1/link-key", 32)`.
  - **Confirm on A only.** B shows the number with "Check that your other device shows the same number, then confirm there." and offers only Cancel. A asks "Does your new device show the same number?" with Match and Don't match, and nothing goes under K before Match.
  - **The bundle.** On Match, A seals a snapshot's plaintext (`takeSnapshot(store, 'link')`: the backup file's JSON without its passphrase layer or any share by link, below) under K: a header blob `{chunks, sha256}`, then the chunks of at most 65,492 bytes, in the bundle mailbox, the unpadded base64url of `HKDF(K, empty salt, "reconcile/v1/link-bundle", 32)`. B skips blobs that don't open, waits until every chunk is there, checks the hash, then `importSnapshot` checks every group as a restore does and keeps them in one transaction as from a link: a group new to B has no backup mark, and one already there keeps its own. B says "Linked. This device now has <n> groups." and syncs.
  - **What travels.** Exactly what a backup file holds, less each personal Document's share by link (#105), and nothing else it leaves out. Format 2's keys and epochs (#98): B lands at each group's current epoch with A's secret and encryption key, opens the wraps of later key changes as A does, and posts no `kx`, since it is the same member and the fold already holds that member's key. Only if A's own `kx` (a member from before #98) hadn't reached the relay when it linked does B post one, carrying the same key, and only the first counts. Every personal Document (#93), merged by id as a restore merges it. Not a dissolved group's read-only copy (#108), which stays on A, and not A's push registration or posted nudges (#99): an endpoint belongs to one device, so B starts with push off and turns it on with its own switch. The relay backup key (#97) travels too, and B keeps it only if it holds none, as a restore does, so B keeps the relay backup fresh. Not a personal Document's share by link (#105, `withoutShares`): a share belongs to the device that made it, since personal Documents don't sync and two devices posting one share would roll its link back and forth. So B gets every Document unshared, posts nothing for A's links and can make links of its own, and A keeps each share and alone can stop it. B drops any share a bundle holds as well, so it keeps a share of its own on a Document the bundle replaces (`restoredCopy`) and never takes up A's.
  - **Ending.** Each side zeroes its seed, one-time secret key and K when it closes: after the bundle, on Don't match or Cancel, when the screen closes, when a send fails, and 10 minutes after the code (A) or after posting `E_B` (B). A poll while one is on its way shares its answer, so a screen can't take two keys or post `E_A` twice.
- **Passkey unlock** (#95; [ADR-0008](../adr/0008-passkeys-and-social-recovery.md), [ADR-0030](../adr/0030-device-key-fallback.md), [ADR-0042](../adr/0042-broad-device-support.md)). Offered once after the pilot notice and always in Settings, in two taps, since iOS allows one WebAuthn call per tap. Only `src/platform/webauthn.ts` calls `navigator.credentials`.
  - Tap 1 is `create()` with `rp: {id: location.hostname, name: 'Reconcile'}`, a random 32-byte user id named "Reconcile key", algorithms −8, −7 and −257, `residentKey: 'preferred'`, `userVerification: 'required'`, `attestation: 'none'` and `extensions: {prf: {}}`. Any PRF answer it gives is ignored. Tap 2 is `get()` for that one credential, with user verification required and PRF evaluated on a random 32-byte salt.
  - That answer decides, once: the keys are sealed only when `prf.results.first` is exactly 32 bytes, the authenticator data's UV flag (0x04) is set, and `prfTrusted` holds (`src/platform/prfPolicy.ts`: false on iOS and iPadOS 18.0–18.3, read from `OS 18_x`, or from `Version/` on an iPad that reports a Mac, and false on an Apple touch device whose version can't be read). Then the vault key is HKDF-SHA-256 of the PRF output, salted with the PRF salt, under `reconcile/v1/key-vault`, and the vault is XChaCha20-Poly1305 under it, a random 24-byte nonce first, with `reconcile/v1/key-vault` ‖ the credential id as associated data (`src/crypto/keyVault.ts`, pinned by `src/crypto/vectors/keyVault.json`, computed outside @noble). Otherwise nothing is sealed: "This device's passkey can't protect your keys, so they stay on this device as before." The PRF output is zeroed either way.
  - Store version 6 adds the `vault` object store after #97's version 5, one version at a time (3 → 4 → 5 → 6), and keeps version 4's groups and personal Documents (#93), which hold no key, and version 5's relay backup state. Sealing moves every secret on the device (today each group's current secret, signing key and encryption key, #98, and the relay backup key, #97) into the one vault record, and deletes the plain copies in the same transaction: the relay backup's record keeps its state without its key. After that, every write of key material (Create group, Join, a backup's or a link's import, a new epoch's secret or encryption key, Leave, Remove, and the relay backup key set, adopted or updated) goes through the store's one write path, `keepKeys`, which reseals the vault with the session's key and refuses while it's locked; every read of the relay backup's state opens the vault too. A shared personal Document's seed and signing key (#105) stay on its record, unsealed, until a follow-up moves them into the vault, as #109's recovery shares will join it. Its launch posts (`keepSharesAlive`) run only once the keys are unlocked, after the sync loop starts. A store opened on a sealed device reads nothing until the passkey's key unlocks it; the key then stays in memory for the session. `Store.requireUnlocked()` is the one check before anything hands keys on: Save a backup calls it, and so does Link a new device (#96), before it shows a code and again before it sends the bundle; a tab whose keys another tab locked shows "Your keys on this device are locked with your passkey. Close Reconcile, open it again and unlock it, then link a new device." instead of a code. A link into a device with a vault writes through `keepKeys`, so what arrives is sealed. Restore on the unlock screen drops the relay backup's state with the vault, and keeps the file's key, if any. Erase never needs it.
  - Nothing about passkeys reaches the relay: the password manager sees the app's host, "Reconcile" and "Reconcile key".
- **Library rule.** Audited libraries only: `@noble/curves`, `@noble/hashes` and `@noble/ciphers`, plus `shamir-secret-sharing` for recovery shares (ADR-0075 §4). **No hand-rolled cryptography.** Randomness comes only from `randomBytes` or `crypto.getRandomValues`. The one other library that touches a secret is `qr` (#96), which draws and reads the linking code and does no cryptography; only `src/app/qr.ts` imports it.

Restored (§11): recovery contacts (#109, #118). Passkey unlock (#95), a second device by scanning a code (#96) and the relay backup (#97) are above. Per-member encryption keys and a new group key on leave (#98) are above and in §4; removal (#115) adds `remove` to `endsMembership`.

## 4. Events

ADR-0006, as ADR-0073 cut it: signed UTF-8 JSON, applied in the relay's order.

### Envelope

```json
{"v": 1, "type": "proposal", "group": "<group id>", "author": "<public key>", "ts": 1762650000000, "body": {}}
```

- The author serializes the event once with `JSON.stringify` to UTF-8. Those exact bytes are signed, sent and hashed, and nobody re-encodes them.
- The event id is the unpadded base64url SHA-256 of those bytes.
- `ts` is the author's clock in milliseconds, for display only.
- Genesis carries `group: ""`, because it can't contain its own hash. The group id is the id of the mailbox's first valid genesis, and every other event carries it.
- Text is NFC-normalized before signing. Atom text also goes through `normalizeAtomText` (#70, `client/src/engine/atomText.ts`, pinned by `vectors/atom-text.json`), in this order: lone surrogates become U+FFFD; CRLF, then any lone CR, becomes LF; NFC; trailing U+0020 and U+0009 leave each line (a trailing NBSP stays, so it is never `trim` or `\s`); and the text ends in exactly one LF. Blank text becomes `""`. Create group normalizes each genesis Atom after splitting at blank lines, and the composer's action normalizes a Proposal's text. A Markdown hard break written as two trailing spaces is therefore lost, so the editor teaches the backslash. The fold never re-normalizes received text, because browsers ship different Unicode tables.

### The fold

`fold(records, relayNow)` turns a mailbox's records, in relay order, into one `GroupState`: the group id (`group`, its genesis id, or null before one), the founding rules (`rules`, §11), the opt-ins in effect (`optIns`, #117), the group's name and chat link, the Document title, members (each with `invitedBy`, the key a verified invite token names, #73, and `received` and `rightsAt`, when the relay received their join and the relay minute their voting rights arrive, #101), former members (`former`: those who left, in the order they left, whose names still show on what they made, #77), Atoms, Proposals with their versions and ballots, outcomes, `at`, the steward seats (`stewards`) and suspensions (`suspensions`, #102), the steward narrowings (`narrowings`, #117), the valid vouches (`vouches`, #101), the chat bot's winning claims (`chatPosts`, #119), each Proposal's Discord thread (`chatThreads`, #123), the Dispatches (`dispatches`, #112), the key's `epoch`, its canonical key changes (`rotations`) and whether one is due (`rotationDue`, #98), `dissolved` (`{received, wipe}` once the group has dissolved, else null, #108), and `ignored` (#63, #69). A member also carries `kx`, their encryption key, or null (#98). Each Proposal carries `number`, its 1-based place among the group's Proposals in relay order, counting only the ones the fold kept (#123; `vectors/proposal-number.json`). A coalition motion opened from `outside` (#100, §4 Coalitions) is 0 and isn't counted, so a group's own numbers don't depend on whether a device has the coalition's log yet (`vectors/coalition-group.json`). `at` is the relay minute the state stands at: the fold sets it to each record's `received` before checking it (it never moves back), and to `relayNow` at the end, or to the latest `received` when that's null, so `can()` reads relay time with its three arguments. Once the group has dissolved, `at` stays at the dissolve's `received` (Dissolution, below). Before each record, and once more at the end, the fold brings the steward seats, the standing opt-ins and the Dispatches passed Proposals carry up to `at` (§4, Stewards and suspensions; Opt-ins; Dispatches). For each record, the fold first checks the epoch of the mailbox it was read from (`LogRecord.epoch`, absent for 0, #98): a record of any other epoch than the group's current one changes nothing, not even `at`, and claims no event id, so the copy its author posts again to the new mailbox folds once. Then it:

1. verifies the signature before it parses the event, and requires `author` to equal the record's key. A record that fails lands in `ignored` with `id: null` and claims no event id, so a forged copy of a real event never shadows it;
2. drops a repeated event id, so the first copy keeps its seq and receipt time;
3. ignores an event whose `v` isn't 1 or whose `group` isn't the genesis id (unknown versions are ignored, ADR-0073), and every event after a `dissolve` (#108). `admits` in `client/src/engine/fold.ts` is this one guard;
4. ignores an event from a non-member, except that person's own `join`: `can()` is false for anyone who isn't a member. It also ignores every event from a member whose suspension is running, except their `leave` (#102, #77);
5. checks the event's rules against the state before it. An event that breaks a rule lands in `ignored` and changes nothing.

### Proposals and ballots

- **Versions** ([ADR-0004](../adr/0004-competing-versions-go-to-ballot.md), [ADR-0047](../adr/0047-ballot-cap-quorum-reproposals.md), #72). A Proposal's own text is version 1, and its id is the Proposal's id. A `version` event's id is its own event id. Versions keep relay order, which the winner's tie rule uses, whatever their `ts`. A ballot holds at most 3 versions (`VERSIONS_MAX`).
- **One open Proposal per Atom** (ADR-0073, #72). A Proposal is open from its receipt until its deadline or its early close, whichever comes first, both in relay order: an event received in the minute of an early close, after the ballot that closed it, finds it closed. The fold ignores a `proposal` on an Atom that has an open one, and new wording joins that one as a version instead. `composeOption(state, atomId)` (`client/src/engine/composeOption.ts`) gives the screens the same rule over folded state: `'propose'` when nothing is open on the Atom, `'add-version'` while its open ballot has room, and `'ballot-full'` at 3 versions. It and the fold share `optionFor`, so the composer never offers what the fold would ignore.
- **Targets** (#75, #102, #117). An edit names an `atom`. An add carries `target: {kind: "add", after: <atom id> | null}` instead, and the new Atom's id is the Proposal's id. An edit whose version text is `""` removes the Atom, and the fold then ignores later Proposals on it. A steward Proposal carries `target: {kind: "steward", seat, member}` and no `atom` or `text` (Stewards and suspensions, below), and so does a rules Proposal, with `target: {kind: "rules", optIn, value}` (Opt-ins, below). A dissolve Proposal carries `target: {kind: "dissolve", wipe}` (Dissolution, below). The folded Proposal keeps its `target`: `{kind: "edit"}` for an edit, the steward change, or the rules change `{kind: "rules", optIn, value, from}`; a steward or rules Proposal's `atom` and `text` are `""`.
- **Eligibility** ([ADR-0015](../adr/0015-anti-capture.md), #77, #90, #101). The eligible voters are the members at the Proposal's place in relay order for whom `wouldVote` holds: people who joined before it and hadn't left, whose voting rights had arrived, at a level that grants `vote`. A later join, leave or level change never changes an open Proposal's eligible set, quorum or early close. A ballot also needs `vote` when the relay receives it, so someone who steps down to Member can't vote until they step back up, while the vote is open.
- **Class and deadline** (#94, #106). `targetClass(state, body)` in `client/src/engine/rules.ts` gives a Proposal its class, `ordinary` or `entrenched`, from the state when it opens. It never reads a field the proposer writes, so nobody can understate a change. The Proposal keeps it as `class`. `chosenWindow(rules, class, body.window)` gives the whole days its vote runs, kept as `window`: the proposer's `window`, or `windows[class].default` when there is none, and null, so the fold ignores the Proposal, for a window `validWindow` refuses. Its deadline is its `received` plus `window` × 1,440 minutes, fixed when it opens: 10,080 for an ordinary change with no window, 14,400 for a window of 10. Early close (below) still applies and doesn't move the deadline. Its versions are tallied at `rules.bars[class]` (§5). A rules Proposal that widens an opt-in from its standing value (`isWider`, Opt-ins below) is entrenched, so with no window it runs 20,160 minutes, its window must be 14 to 28 days, and it needs the entrenched bar (#117). Every other target is ordinary, steward elections and recalls included (ADR-0049), until entrenched sections (#116) and removal (#115) each add their case to `targetClass`. Dissolving the group is entrenched (#108). A steward Proposal carries no `window` and runs its class's default: 7 days.
- **Ballots.** A ballot scores versions by version id. A voter's latest valid ballot replaces their earlier one in full, so a version it leaves out loses that voter's score. A ballot that names a version not yet on the Proposal, in relay order, is ignored, even once that version arrives, and so is a ballot received after the deadline or the close. An ignored ballot never replaces the voter's earlier one.
- **Close.** A Proposal closes early at the first ballot after which every eligible member's latest ballot scores every version; `closedAt` is that ballot's `received`. Otherwise it closes once `relayNow` reaches the deadline. A new version restarts the wait for an early close: it closes only once every eligible member's latest ballot scores the new version too.
- **Apply.** Only a closed Proposal's outcome is final. A final pass sets the target Atom's text, or adds or removes the Atom. Final passes apply in order of close time (`closedAt`, or else the deadline), with ties broken by the Proposal's relay order, so every device builds the same Document.
- **Leave** (#77). After `leave`, `can()` refuses the author everything, so the fold ignores their later events, a join under the same key included. Ballots received before the leave still count, and the leaver's Proposals and versions stay on the ballot. An open Proposal keeps them in its eligible set, so its quorum and early close don't change, and a Proposal that opens later leaves them out. `applyLeave` in `client/src/engine/fold.ts` is the one place a leave takes effect, so whatever else a member holds, such as a steward's seat (#102), empties there. `displayName` names former members too, so their ballots and Proposals still say who. Golden vectors: `vectors/leave-*.json`.

### Stewards and suspensions

#102 builds them in `client/src/engine/stewards.ts` ([ADR-0016](../adr/0016-suspend-then-vote.md), [ADR-0049](../adr/0049-stewards-and-removal.md), [ADR-0059](../adr/0059-suspension-during-removal.md), [ADR-0072](../adr/0072-protocol-details-for-decomposition.md) §4, [ADR-0075](../adr/0075-safeguards-for-the-revised-mvp.md) §3). The fold and the screens ask the same functions there (`mayProposeSteward`, `maySuspend`, `electionsDue`), so a screen never offers what the fold would ignore.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `proposal` with a steward target | `{target: {kind: "steward", seat, member}, title, why, link?}`: the seat (a whole number), the nominee's key, or `null` for a recall of the seat's steward. Any `window` is left out, so it runs its class's default (#106) | the author holds `propose`; the title is 1–120 code points and the justification at most 2,000; the seat is 1 or 2 and has no open steward Proposal; seat 1 needs `stewards.firstElectionAt` (3) voting members until its first election has passed, and an election for seat 2 needs `stewards.secondSeatAt` (6). An election's nominee is a member who holds voting rights at a level that votes (`wouldVote`), isn't suspended, and doesn't hold the other seat. A recall needs a holder | #102 |
| `suspend` | `{member, reason?}`: the member suspended, and a reason of at most 280 code points (ADR-0072 §4) | `can(author, 'suspend')`; the member is a current member other than the author and isn't suspended; their last suspension ended more than 30 days earlier; the author holds no other running suspension; and no recall of the author is open | #102 |

- **Seats.** `state.stewards` holds seat 1 and seat 2 as `{seat, holder, termEnd, elected}`. The genesis author holds seat 1 with no term end (`termEnd: null`) until an election passes. "Voting members" are counted by `votingRightsCount(state)` in `capabilities.ts`: the people holding voting rights, whatever level they chose, ignoring suspensions (ADR-0075 §3, #101).
- **Elections and recalls.** A steward Proposal is ordinary, opens with one version under its own id and no text, and takes no `version` events. A recall's eligible set leaves out the steward it would remove, or their own 0 alone would block it in a group of 10 or fewer. The folded target also records `holder`, who held the seat when it opened.
- **Seating.** The fold applies a steward Proposal once it closes, in order of close time, then relay order. A pass seats the nominee for a term ending `stewards.termDays` × 1,440 minutes after the close (262,080), but seat 2's first-ever term is 91 days (131,040), so the seats come due about three months apart. The nominee is seated only if their level still votes and they don't hold the other seat; a suspension doesn't stop it, so a steward can't block an election by suspending the nominee. A recall's pass empties the seat if the steward it named still holds it.
- **Emptying a seat.** A seat empties when its holder steps down to a level that doesn't vote, on a recall, and, through `vacate` in `stewards.ts`, on the holder's `leave` (#77) and removal (#115). Past its term end a holder keeps the seat until a successor is seated; seat 2 can seat none below 6 voting members, so in a group that has shrunk below 6 it empties at its term end. `electionsDue(state)` lists the seats whose election could open now and that are empty, held by the founder before the first election, or past their term end.
- **Suspensions.** `state.suspensions` keeps every suspension in relay order as `{id, seq, received, by, member, reason, until}`. One runs from its `received` until `until`, `received` + `suspensionDays` × 1,440 (10,080 minutes). Meanwhile `can()` gives the member only `read` and `see-roster`, and the fold ignores their events (§4, The fold) apart from their `leave`, since exit is always possible (ADR-0010, #77). Ballots received before it still count, and a later ballot doesn't replace them. They stay in the eligible set of Proposals that open during it (`wouldVote` ignores suspensions), so a suspension never shrinks the electorate, and those Proposals can't close early without them. Stewards can't lengthen or lift one; #115's open removal vote is the only thing that extends it (ADR-0059). The reason stays in the signed log; expiring it stays deferred (ADR-0074).

### Opt-ins

#117 builds them in `client/src/engine/optIns.ts`, with the steward's narrowing in `stewards.ts` ([ADR-0038](../adr/0038-optional-discovery.md), [ADR-0039](../adr/0039-integrations-per-group-opt-in.md), [ADR-0040](../adr/0040-group-opt-ins-are-governed.md), ADR-0074, ADR-0075 §3 and §5). A group has two opt-ins, both off at founding: the Discord chat bot (`chatBot`: `null`, or `{webhook}`), which posts content-free nudges, ADR-0039's step 1 (#119, Chat bot below); and the front door (`frontDoor`: `false`, or `{sign, box, showCount}` once open), whose page #121 builds (Front door, below). Each changes only by a rules Proposal, never by a toggle. The screens ask the same functions the fold does (`mayProposeRules`, `mayTurnOffNow`), so a screen never offers what the fold would ignore.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `proposal` with a rules target | `{target: {kind: "rules", optIn, value}, title, why, link?, window?}`: the opt-in and the value it would set, kept as written, and the voting window in whole days (#106) | the author holds `propose`; the title is 1–120 code points and the justification at most 2,000; `optIn` is `chatBot` or `frontDoor`; `value` passes that opt-in's validator and differs from its standing value; no other rules Proposal for that opt-in is open; and `window`, when present, is within `windows[class]` for the class `targetClass` gives it (14 to 28 days to turn one on, 3 to 14 to turn one off). The chat bot's validator takes `null` or `{webhook}` with no other field, where the webhook is the whole string `https://discord.com/api/webhooks/<digits>/<token>` (or `discordapp.com`), with a token of letters, digits, `_` and `-`, and no port, user, query, fragment or capital in the host. It is one pattern over the string, never a URL parser, so every browser folds the same answer. The front door's takes `false`, or exactly `{sign, box, showCount}`: two 32-byte secrets in canonical unpadded base64url and a boolean, with no other field (#121) | #117 |
| `narrow` | `{optIn, proposal}`: the opt-in, and the author's own off-Proposal for it | `can(author, 'narrow')`; no recall of the author is open; the opt-in isn't off in effect; `proposal` is an open rules Proposal for that opt-in, setting it to off (`null` or `false`), by the same author; and no off-Proposal for that opt-in failed or lapsed within the last 30 × 1,440 minutes: a `narrow` received 43,200 minutes or fewer after such a close is ignored | #117 |

- **Standing value.** `state.rules.optIns` holds each opt-in's standing value: the founding default (a genesis can't open one, §11), then the value of the last rules Proposal for it that passed, applied once it closes, in order of close time, then relay order, as the steward seats are.
- **Class.** `isWider(optIn, from, to)` is true from off to on, and for the front door from hiding its count to showing it (#121), so turning an opt-in on, or showing the count, is entrenched (a window of 14 to 28 days, 14 by default, and the entrenched bar), and turning it off, replacing one webhook with another, rotating a front door's keys or hiding its count is ordinary (3 to 14 days, 7 by default, and the ordinary bar; ADR-0075 §5). `targetClass` reads the standing value when the Proposal opens, and the fold records it as the target's `from`, so a proposer can't understate the change. A rules Proposal opens with one version under its own id and no text, and takes no `version` events.
- **Narrowing.** `state.narrowings` keeps every steward narrowing in relay order as `{id, seq, received, by, optIn, proposal}`. From the `narrow`'s receipt, the opt-in is off until its off-Proposal closes: off for good if that passes, and back to the standing value at its close if it fails or lapses (ADR-0040, ADR-0075 §3). Every member reads it: Group rules names the steward who turned it off, and the off-Proposal's ballot says so too.
- **Effective value.** `effectiveOptIn(state, optIn)` is off while a narrowing of it is in force and the standing value otherwise; `state.optIns` holds each one's effective value at `at`. The chat bot (#119) and the front door (#121) read only the effective value.
- **The webhook is a credential.** Anyone holding it can post into the channel. It exists only inside sealed group events and in folded state on members' devices, never readable at the relay, and screens show only its last 4 characters (§9).

### Dissolution

#108 builds it in `client/src/engine/dissolve.ts` and `fold.ts` ([ADR-0051](../adr/0051-dissolution-and-rule-classes.md), [ADR-0072](../adr/0072-protocol-details-for-decomposition.md) §10, [ADR-0075](../adr/0075-safeguards-for-the-revised-mvp.md) §5). The fold and the screens ask the same functions there (`mayProposeDissolve`, `dissolveDue`, `closedByDissolve`), so a screen never offers what the fold would ignore.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `proposal` with a dissolve target | `{target: {kind: "dissolve", wipe}, title, why, link?, window?}`: `wipe` is `true` or `false` (anything else is a bad shape), and whether every device also erases the group. Any `text` is dropped, and an `atom` makes it a bad shape | the group hasn't dissolved; the author holds `propose`; no other dissolve Proposal is open; the title is 1–120 code points and the justification at most 2,000; and any `window` passes `validWindow` for the entrenched class: 14 to 28 days, default 14 | #108 |
| `dissolve` | `{proposal}`: the dissolve Proposal whose pass is final; any other field is dropped | the group hasn't dissolved; the author is a member (`can(author, 'read')`), a newcomer still earning a vote included (#101); and `proposal` names a dissolve Proposal that, at this event's receipt, has closed (early, or at its deadline) with a pass at the entrenched bar | #108 |

- **The vote.** A dissolve Proposal is entrenched (§5's `{3, 5}` bar, `rules.windows.entrenched`), opens with one version under its own id and no text, takes no `version` events, and has everyone `wouldVote` lets in, so holding voting rights at a level that votes (#101), in its eligible set. Competing dissolve versions stay deferred.
- **The event.** Any member's device that folds the final pass, while no `dissolve` has folded, posts one (`settleDissolve`, §7). The fold takes the first valid one and sets `state.dissolved = {received, wipe}`.
- **After it.** The fold ignores every later event, a second `dissolve` included, and relay time stops at its receipt: `at` stays there, and so does the minute every Proposal is settled at. A Proposal still open then never closes: it applies no text, seats nobody, and has no outcome (`final` stays false), and the screens read "Closed when the group dissolved". No `vouch` lands, and a newcomer's wait still running then never ends: a `rightsAt` later than the dissolve's receipt never arrives, so they never hold rights (#101). Golden vectors: `vectors/dissolve-*.json`.

### Chat bot

#119 builds it: the moments and the claim rule in `client/src/engine/chatPosts.ts`, the posting in `client/src/store/chatBot.ts`, and the request in `client/src/net/discord.ts` (ADR-0039 step 1, ADR-0074). While a group has its bot on in effect (`effectiveOptIn(state, 'chatBot')`), its Discord channel hears of each Proposal, steward and rules Proposals included, three times. No server holds the webhook, so one member's device posts each notice, and the log decides which.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `chat-posted` | `{proposal, moment, nonce?}`: the Proposal, the moment claimed (`open`, `closing` or `result`), and 16 random bytes in base64url that the fold doesn't read, so two devices holding one key (#78) never sign the same bytes | the author is a member who isn't suspended; the bot is on in effect at its receipt (neither off nor narrowed); `proposal` is one of the group's own Proposals in the fold, never a coalition motion (#100), which has no number for a thread's name; `moment` is the one due at its receipt (below); and no claim of that (Proposal, moment) was kept before it. The first valid claim wins, in relay order | #119 |
| `chat-thread` | `{proposal, url}`: the Proposal, and the link to the Discord forum thread its opening notice opened | the author is a member who isn't suspended and made the winning `open` claim for that Proposal, so no other member can point Join discussion at another server; the bot is on in effect at its receipt; `url` is the whole string `https://discord.com/channels/{server id}/{thread id}`, each id 17 to 20 digits (`^https://discord\.com/channels/\d{17,20}/\d{17,20}$`, one pattern over the string); and no thread was kept for that Proposal before it. The first valid one wins, in relay order | #123 |

- **Moments.** At any relay minute at most one moment of a Proposal is due (`dueMoment`). `open`: from its receipt until it closes or until `deadline − 1,440`, whichever comes first. `closing`: from `deadline − 1,440` until it closes. `result`: from its close (`closedAt`, or else `deadline`) until 1,440 minutes after. A vote that closes early before its last day skips `closing`. Because the fold checks a claim against the moment due at its receipt, nobody can claim a moment early to silence it, and turning the bot on or joining never replays an old result. There is no `version` notice.
- **Winning claims.** `state.chatPosts` keeps each winning claim in relay order as `{id, seq, received, by, proposal, moment}`. The fold and the devices ask the same function (`mayClaim`), so a device never makes a claim the fold would ignore.
- **Claim, then post** (`createChatBot`, run by the sync loop after each group syncs, §7). While the bot is on, the device enqueues a `chat-posted` for each moment due at the relay's `now` that has no winning claim and that it hasn't claimed already, and keeps the claim's id in the group's record (`chatClaims`). It posts a claim only when the winning claim's id is one it made and that moment is still due at `now`, settling the claim first in one store change, so two tabs can't both post it, and never retries. It drops a claim another claim beat, one the fold ignored, and one whose moment has passed. While a steward's narrowing holds the bot off, a winning claim waits, and goes out if the bot comes back on while its moment is still due. A device whose group is leaving (#77) claims and posts nothing, and so does one whose group has dissolved (#108): it posts no notice, not even the dissolve's result, and keeps no claim. A slow or failing Discord never holds up sync. A closing or result notice therefore goes out the next time any member's app syncs after that moment.
- **The post** (`postWebhook`). It checks the webhook with the opt-in's own validator and refuses anything else before `fetch` runs, rebuilds the URL as `https://discord.com/api/webhooks/{id}/{token}` (so a `discordapp.com` webhook works under the CSP and nothing else in it survives), and POSTs `{"content": …, "allowed_mentions": {"parse": []}}` as JSON with `credentials: 'omit'`, `referrerPolicy: 'no-referrer'`, `cache: 'no-store'` and `redirect: 'error'`. The content is `chatMessage(moment, {deadline})` with no title (#113), a line break, then the app's origin and `/`: "A new Proposal is open in Reconcile. Voting ends Fri 14 Nov.", "A vote closes within a day in Reconcile." or "A vote has finished in Reconcile.". It is made from the moment and the deadline alone (`botNotice`), so no title, name, count or Document text can reach it.
- **A thread per Proposal** (#123; [ADR-0011](../adr/0011-debate-venues.md), ADR-0039: step 1 carries no titles, so threads are numbered, not named). With a forum channel's webhook, each Proposal gets its own Discord thread, and at most three posts in it.
  - **Opening it.** A post for a Proposal with no thread in the log sends `?wait=true` and `thread_name: 'Proposal {number} in Reconcile'` (`botThreadName`). A text channel may refuse that with a 400: the device sends the post once more without it, as above. Or it may post it in the webhook's own channel. Once a post without it is taken, or the message is seen to land in that channel, this device remembers in the group's record (`chatChannel`, by the webhook's id, never its token) that the webhook takes no threads, and posts as above from then on.
  - **Recording it.** Otherwise, when the post was the opening of a Proposal whose winning `open` claim is this device's (`mayRecordThread`), the device reads the webhook's `guild_id` and `channel_id` once per group (`getWebhook`: a GET of `https://discord.com/api/webhooks/{id}/{token}` with no body, cookie, referrer or cache, following no redirect, reading only those two ids), and keeps them in `chatChannel`. When the message's `channel_id` differs from the webhook's, it's a new thread, and the device enqueues `chat-thread {proposal, url: 'https://discord.com/channels/{guild}/{thread}'}`. `state.chatThreads` keeps each kept thread as `{id, seq, received, by, proposal, url}`, and `threadFor(state, proposal)` reads it. A Proposal whose opening went unclaimed, such as the vote that turned the bot on, opens a thread with its first post and records none.
  - **Later posts** for that Proposal add `?thread_id={thread}`. In the thread, the `result` post reads "The argument has concluded. A vote has finished in Reconcile.", then the app's address. A group's posts go out one after another, so each sees what the one before learned.
  - Every request stays on the webhook's own path, so the CSP's `connect-src` needs nothing new: a source's path never matches the query. Deferred past the MVP: thread titles, reading or mirroring a thread, archiving or locking threads, a bot with its own token, and threads on other platforms.
- **What Discord learns** (ADR-0039, §9): that the group uses Reconcile, when its votes open, enter their last day and close, each Proposal's number in the name of its thread (and so how many Proposals the group has made), the app's address (a cross-origin request always carries its origin), and the address of the device that posts, with that browser's ordinary request headers. Never a cookie, a referrer, a title, a name or anything else of the group. The relay sees each claim and each thread link as one more sealed blob, and the thread link points into the group's own Discord server.

### Front door

#121 builds it: the keys and boxes in `client/src/crypto/door.ts`, the invite record in `client/src/engine/frontDoor.ts`, and the page, Send, the inbox and the keeper in `client/src/door/` ([ADR-0038](../adr/0038-optional-discovery.md), [ADR-0014](../adr/0014-invite-and-vouch-admission.md), ADR-0040, ADR-0075 §5). Devices act only on `effectiveOptIn(state, 'frontDoor')`, so a steward's narrowing closes the door at once.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `door-invited` | `{application}`: the SHA-256, in unpadded base64url, of the sealed application blob an invite answered | the author holds `invite` (`can()`); the door is open in effect; `application` is 32 bytes in canonical base64url; and no `door-invited` for it has folded. The first valid one per application wins (`mayRecordInvite`) | #121 |

- **Opening.** The opt-in composer makes the door's two secrets on the proposer's device: `sign`, an Ed25519 secret key whose public half is the door's address, and `box`, an X25519 secret key. They travel only inside the rules Proposal, in the sealed log. The link is `${origin}/#door/${address}`, the 43-character address, which is no secret, so it stays in the address bar.
- **Derivations.** HKDF-SHA-256 (§3) of the address derives the page mailbox (`"reconcile/v1/door-page"`), the page seal key (`"reconcile/v1/door-page-key"`) and the inbox (`"reconcile/v1/door-inbox"`); of a reply seed, the reply mailbox (`"reconcile/v1/door-reply"`). `vectors/door.json` pins them, a signed page and two boxes, computed outside @noble.
- **The page** is UTF-8 JSON, `{v: 1, open: true, name, excerpt, count?, box}` or `{v: 1, open: false}`: the group's name (120 code points and "…" at most), the first section of its Document as plain text cut to 280 code points and "…", the member count only while `showCount` holds, and the X25519 public key of `box`. It's signed with `sign` under the tag `reconcile/v1/door-page`, sealed under the page key, and PUT with `ttl_days=30`. Readers take the last copy in relay order whose signature verifies and whose page parses exactly; no valid copy reads as closed.
- **The keeper** (`createDoorKeeper`, run by the sync loop after each group syncs and, for replies, after each complete pass, §7). While the door is open in effect, a member's device posts the page when the newest copy says otherwise or is 7 days (10,080 minutes) old in relay time. Every other door the group had stand (rotated away, closed, narrowed, or in a dissolved group) gets `{v: 1, open: false}` once, while its newest copy still says open. A member who holds `invite` reads the inbox after its cursor while the door is open in effect, and no device reads it otherwise; what it reads stays on the group's record on that device (`door`), never in a backup, and goes with Leave or an archive.
- **Applying** (`#door/{address}`, below in §8). Send makes a reply X25519 key and a 32-byte reply seed and keeps both on the device, in a store of their own (`sent`), then PUTs `{name, message, reply: {seed, key}}` (a name of 1 to 120 code points, a message of up to 2,000, and the reply seed and public key) sealed to the page's `box` to the inbox with `ttl_days=30`. A padded box is `box.ts`'s box of a body framed as a seal's, sized so the box is one of the four blob sizes, with the mailbox id as AAD.
- **Answering.** 'Send an invite' makes an ordinary invite (§3), seals its link to the applicant's reply key, padded, PUTs it to the reply mailbox with `ttl_days=2`, then queues `door-invited`. For 30 days by its own clock, the applicant's device reads each pending application's reply mailbox after every complete sync pass and keeps the invite seed from the latest reply that opens; Join forgets the application once it's used.
- **What the relay sees:** padded blobs in three mailboxes it can't link to the group or to each other, and the IP addresses of the devices that post and read them, as for any sync. The page and the inbox keep one id each for the door's life, like an invite's mailbox, and don't rotate weekly as group traffic does (#110): the link is published, so anyone holding it derives every id it would rotate to, and rotation would hide nothing from them. What a fixed id lets the relay link is the door's own traffic over time: how often its page is posted and read, how many applications arrive and when, and the addresses that post or read them. Rotating the door's keys, an ordinary change, moves both to new ids, and the old page closes.

### Dispatches

#112 builds them in `client/src/engine/dispatches.ts` and `fold.ts` ([ADR-0003](../adr/0003-three-tier-involvement-levels.md), [ADR-0012](../adr/0012-content-free-push.md), ADR-0074). A Dispatch is news for the whole group: a title, a short plain text and, optionally, a Document it points to. A Co-Creator sends one, or a Proposal carries one that goes out when it passes ("Updated: Mission statement"). Every level follows the group and reads its Dispatches; the Dispatch's text lives only in the sealed group log, and the push it rides says only "Something new in Reconcile" (§7, Push). Scheduled weekly or monthly Dispatches, the digest, targeting particular people, "new" dots, and editing or deleting a Dispatch stay deferred (ADR-0074, §12).

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `dispatch` | `{title, text, doc?}`: the title, the text, and the id of a Document it points to | the author holds `dispatch` (`can()`: a Co-Creator holding voting rights who isn't suspended); the title is 1–80 code points and the text at most 500 (`dispatchFits`); and `doc`, when present, is the id of one of the group's Documents (`documentIds`: the `documentId` of an Atom in state) | #112 |

- **Carried by a Proposal.** Any `proposal`, an edit or a targeted one (§4, Proposals and ballots), may carry `dispatch: {title, text}` with the same limits; a `proposal` whose `dispatch` breaks them is ignored whole, and any other key inside it, a `doc` included, is dropped. The folded Proposal keeps it as `dispatch`, or null. When its pass is final, the fold appends a Dispatch with `id` and `by: {proposal: id}` set to the Proposal's id, `doc` set to the Document it changed (its Atom's `documentId` for an edit, null for a steward, rules or dissolve Proposal), and `received` set to its close time (`closedAt`, or else the deadline). A fail or a lapse sends nothing, nor does a Proposal still open when its group dissolves (#108). Its push is the result's wake (§7, Push).
- **Order.** `state.dispatches` keeps each Dispatch as `{id, by, title, text, doc, received}`, with `doc` null when there is none, in the order they went out: a sent one at its receipt, in relay order, and the ones passed Proposals carry, brought up to `at` before each record like the steward seats, in close order (close time, then the Proposal's relay order), ahead of every record received from their close on. So `received` never goes down along the list. The Dispatches view lists them newest first (`newestFirst`).
- **Lengths** count code points as received, like every other limit: the author's device normalizes to NFC before signing, and the fold never re-normalizes (§4, Envelope). The screens count with `nfcLength` before sending.

### Vouches and the wait before voting

#101 builds them in `client/src/engine/admission.ts` ([ADR-0014](../adr/0014-invite-and-vouch-admission.md), [ADR-0021](../adr/0021-level-names-and-self-selection.md), [ADR-0049](../adr/0049-stewards-and-removal.md), [ADR-0075](../adr/0075-safeguards-for-the-revised-mvp.md) §3). Anyone with a live invite link joins and reads at once, but a newcomer earns a vote. The fold and the screens ask the same functions there (`mayVouch`, `vouchWanted`, `admissionOf`), so a screen never offers a vouch the fold would ignore.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `vouch` | `{member}`: the newcomer's key | the group hasn't dissolved (#108); `can(author, 'vouch')` (a voting level, with rights, not suspended); `member` is a current member other than the author; and the author hasn't vouched for them before. Duplicates and self-vouches are ignored | #101 |

- **Rights.** Each member's `rightsAt` is the relay minute their voting rights arrive, or null: genesis's `received` for the founder; their join's `received` for a bootstrap joiner; and for anyone else the later of their join's `received` + `waitDays` × 1,440 (20,160) and the `received` of their `vouches`-th (2nd) valid vouch, set by that vouch and never moved. The wait runs on relay receipt, never the author's `ts` (ADR-0073). Rights once earned stay, so stepping down to Member and back up needs no new vouch. A vouch from someone who later leaves still counts. `rightsAt(state, member)` reads it, for members and former members.
- **Bootstrap.** A join holds rights at once while fewer than `stewards.firstElectionAt` (3) people, members or former, have held rights by its receipt, counting the founder: the founder and the first two joiners. It counts people, whatever level they chose, so joiners who pick Member still use it up, and it never reopens when someone leaves or steps down (ADR-0049: it ends when the first steward election opens).
- **The gate.** Until `rightsAt ≤ state.at`, `can()` grants a member only a Member's capabilities (`NEWCOMER_CAPABILITIES`), whatever level they chose, so their `proposal`, `version`, `vote` and `vouch` are ignored and `wouldVote` leaves them out of the eligible set. From then on their chosen level applies. `votingRightsCount(state)` counts the members whose rights have arrived, whatever level they chose: ADR-0075 §3's one count of "voting members", which the steward thresholds read.
- **Privacy.** Vouches show who knows whom, so they live only in the group's sealed log, and every member reads them as they read ballots ([ADR-0010](../adr/0010-open-ballots-with-exit.md)). Nothing new reaches the relay.
- Golden vectors: `vectors/vouch-*.json` and `vectors/bootstrap-*.json`. Deferred past the MVP: penalties for vouching a fake account, withdrawing a vouch, recovery before voting ([ADR-0052](../adr/0052-newcomer-onboarding.md)), the mass-join alert, invite caps and per-group vouch counts.

### Encryption keys and a new group key

#98 builds them in `client/src/crypto/box.ts`, `client/src/crypto/epoch.ts`, the fold, and `client/src/store/epochs.ts` and `sync.ts` ([ADR-0009](../adr/0009-per-group-identities.md), [ADR-0072](../adr/0072-protocol-details-for-decomposition.md) item 11, ADR-0073, ADR-0074). When a membership ends, the group gets a new secret that only the members who remain can open, and moves to the mailbox it derives.

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `kx` | `{kx}`: the author's X25519 public key, 32 bytes in canonical base64url | the author is a member with no `kx` yet: the first per member counts, and one their `genesis` or `join` carried came first. A key of low order (one of the five @noble refuses) counts as none, at genesis, join or here, so nobody can post a key no box can be sealed to and stop the key from ever changing | #98 |
| `key-rotate` | `{epoch, commit, wraps}`: the next epoch (a u32 from 1), its commit, and one wrap per member key | a current member wrote it; an event for which `endsMembership` holds (`leave`; #115 adds `remove`) has applied since the last canonical key change, or genesis; `epoch` is the current one plus 1; and the wraps' keys are **exactly** the current members that have a `kx`. The first valid one per epoch is canonical (relay order decides, ADR-0073) | #98 |

- **Commit and wraps** (`epoch.ts`). `commit` is the base64url SHA-256 of UTF-8 `reconcile/v1/epoch-commit` ‖ `0x00` ‖ the group id's UTF-8 ‖ u32be(epoch) ‖ the 32-byte secret. Each wrap is a box (§3) of the secret sealed to the member's `kx` under info `reconcile/v1/epoch-wrap`, with the group id ‖ u32be(epoch) ‖ the member's key ‖ the commit as associated data, each text in UTF-8 as the event spells it, so a wrap moved to another member, epoch or group never opens. A wrap that opens to a secret that doesn't match the commit counts as missing.
- **Epochs.** Each canonical key change moves the group to its epoch. A record read from any week's mailbox of epoch e after e's key change changes nothing (§4, The fold), so a stale invite's join and a late writer's event are ignored there. Relay seqs are global, so a device's log holds records of several mailboxes, merged by seq (§7, Each pass); invite chunks and the backup carry each record's epoch.
- **The duty** (`sync.ts`). After a pass in which every group synced, a device whose member is current, holds the current epoch's secret and isn't leaving, and that sees a key change due, syncs that group once more. If one is still due, it makes a fresh secret, wraps it to every current member with a `kx` (itself included), wipes it, and posts the signed `key-rotate` straight to the outgoing epoch's mailbox for the week its relay minute falls in (#110). It learns the new secret as every other device does, from its own wrap. Devices that race each post one; the fold keeps the first.
- **The freeze.** While a key change is due, or the fold has one this device hasn't taken up, the outbox sends only `key-rotate` and `leave`, and everything else waits in its place.
- **The switch.** A pull that brings a canonical key change into the next epoch whose wrap for this member opens moves the group, in the same store change: the new secret and epoch, a base cursor at the key change's seq for the new epoch's mailboxes (they hold nothing earlier) with no cursor of the old epoch's, and this member's own records that landed in any of the old epoch's mailboxes after the key change, put first in the outbox to post again. The device reads the new epoch's mailboxes at once and stops reading the old ones; GET is ascending, so everything before the key change is already in. A later key change in the new mailbox moves it again in the same pass.
- **No wrap.** A device with no wrap that opens stays where it is. Group home says "You left this group on another device." when this membership has left, and otherwise "This group's key changed and this device didn't get the new one. Ask someone in the group for a new invite link.", and offers no invite link. A newer invite's merge (§7) brings the current secret, once it matches its key change's commit, and the frozen outbox goes to the new mailbox.
- **Who it covers.** Everyone in the group is a member for this, at any level and before their voting rights arrive (#101), so all of them get a wrap.
- **After a dissolve** (#108). The fold ignores every event after a `dissolve`, a `leave` and a `key-rotate` included, so no key change becomes due or lands after it, and the dissolve itself clears `rotationDue`, even when a leave folded just before it with no key change yet. A dissolved group's devices archive it, so none takes the duty, posts a `kx` or holds an outbox frozen: the outbox is gone, and the loop sends and reads nothing for it (§7, Dissolve). A dissolved group's home shows its archive note, never a no-wrap line. Golden vectors: `vectors/dissolve-rotate.json`.
- Golden vectors: `vectors/rotate-*.json`, and the fast-check property that a record read from another epoch's mailbox, anywhere, changes nothing. Deferred past the MVP (#98): MLS, key-grant and unwrap-failure events, re-sending a key change (a device away past 30 days uses §7's catch-up line), clearing a leaver's other device, and revoking live invite envelopes. Until unwrap-failure events land, a current member who posts a valid-looking key change with wraps that don't open leaves everyone on the no-wrap line.

### Coalitions

#100 builds the engine in `client/src/engine/coalition.ts`, `crossing.ts` and `fold.ts` ([ADR-0036](../adr/0036-coalition-each-group-passes.md), ADR-0009, ADR-0073, ADR-0074, [ADR-0075](../adr/0075-safeguards-for-the-revised-mvp.md) §1), with no screens yet (#114, #120). A coalition is a log of its own, with the same signed records, ids, relay order and relay time as a group's, whose members are groups. `fold` folds it too: a coalition's state is a `GroupState` whose `coalition` is `{status, declinedAt, seats, founding, formsBy, bindings, results, motions}` (null for a group). A group's `coalitions` lists its reconcile Proposals as `{proposal, key, name, title, atoms, outcome}`, `outcome` being `open` until its vote is final, then `pass` or `fail` (a lapse is a fail).

| Type | Body | Valid when | Built by |
|---|---|---|---|
| `proposal` with a reconcile target (in a group) | `{target: {kind: "reconcile", secret, inner, seat, name, title, atoms}, title, why, link?, window?, dispatch?}`: the coalition secret; `inner`, 32 random bytes followers never get, for #125's room and #122's higher seats; the group's 32-byte seat secret, each in canonical base64url; and the coalition's proposed name and statement; and an optional Dispatch it sends the group if it passes (#112). Any `text` is dropped | the author holds `propose`; the title is 1–120 code points and the justification at most 2,000; any `window` passes `validWindow` for the ordinary class; any `dispatch` fits a Dispatch's limits; and no earlier reconcile Proposal here holds the same seat key. It is ordinary, with one version under its own id and no text. The fold keeps the target as written, plus `key`, the public seat key | #100 |
| `genesis` with `kind: "coalition"` | `{kind: "coalition", name, chat?, title, atoms, rules?, seats: [{name, key}]}`: a group genesis body with no founder, plus each founding group's name there and public seat key | it is the first valid event in the mailbox; `rules` founds a group (§11); and the seats hold two or more distinct keys. Its author isn't a participant, so it has no members until people join | #100 |
| `join` (in a coalition) | `{name, seat, proof}`: the participant's coalition name, the seat they come from, and its seat proof (§3). `level`, `token` and `kx` are never read | the author hasn't joined, `seat` is one of the coalition's seats, and `proof` verifies for the author's key and this coalition. They take part at `PARTICIPANT_LEVEL`, the creating level, with rights at once and no `kx`, and `bindings` records their seat | #100 |
| `proposal` (in a coalition) | an edit of one of the coalition's Atoms, as in a group | the coalition has formed, and the group fold's rules for an edit hold. It is a **motion**, with its deadline and bar from the coalition's rules, and `motions` keeps a snapshot of the seats at its receipt. A steward, rules, dissolve or reconcile target is ignored here: their effects would apply while a pass can still be contested, and reconciling a coalition is #122's. So is a motion carrying a Dispatch (#112): it would go out at a close a contest can still undo, and a coalition's followers are #124's | #100 |
| `group-result` | `{motion, seat, result}`, exactly those keys, `result` being `pass` or `fail`; any other key makes it a bad shape | it is in a coalition's log; the author is a current participant bound to `seat`; `seat` decides `motion` (the genesis's seats when `motion` is the genesis id, else the motion's snapshot); results on it still count (below); and the same result isn't already recorded for that motion and seat | #100 |

- **What a coalition takes.** Only `genesis`, `join`, `proposal`, `group-result` and `leave`. Every other type is ignored there, `vote`, `version`, `chat-posted`, `chat-thread` and `dispatch` included, so a motion has one version and no ballots, and `kx` and key changes don't apply: a `leave` ends only that participant. A group's own log ignores `group-result`.
- **Forming** (ADR-0036). A coalition is `forming` until every founding seat has reported `pass` on the genesis id, then `formed`, however many seats there are. A `fail` from any founding seat, a contest included, makes it `declined` at once, even after it formed: forming needs every founding group. Results on the genesis count until `formsBy`, the genesis's receipt plus `windows.ordinary.max` days (the latest a founding group's reconcile vote can close) plus 10,080 minutes, and a coalition still forming then is declined there. Once declined, the fold ignores every later event and relay time stops, as after a dissolve. A `proposal` before it forms is ignored.
- **Results that cross** (ADR-0036, ADR-0075 §1). A seat counts once per motion: `fail` if it ever reported `fail`, else `pass` if it reported `pass` (`seatResult`). So a seat that reports both is **contested** and counts as a fail, in either order: anyone holding the seat secret, a former member included, can block a motion but never pass one. Results on a motion count while their receipt is before its deadline plus 10,080 minutes (`RESULT_GRACE_MINUTES`).
- **Deciding a motion** (`coalitionOutcome`, §5). A fail is final at once, and the motion closes there (`closedAt`). A pass is final only once results stop counting, at deadline + 10,080, since until then a contest could still turn it into a fail; until then it reads as a pass that isn't final, and the coalition's Atoms don't change. A final pass changes the Atoms as an edit's does in a group. A motion not yet decided reads as a lapse, as an unscored Proposal does.
- **Motions open in every group** (`crossing.ts`). `motionsFor(coalition, seatKey)` gives `{id, coalition, seq, received, class, window, deadline, bar}` for each motion whose snapshot holds the seat, and `fold(records, relayNow, outside)` opens each in the group as a Proposal right after the group's records with a lower relay seq: relay time moves on to its receipt, its eligible set is everyone `wouldVote` lets in there, and the group's ballots, early close, deadline and `tally()` at the motion's bar apply as usual. It has `target: {kind: "motion", coalition, bar}`, one version under the motion's id, and no title, text or author: the screens read those from the coalition. It isn't the group's own, so its `number` is 0 and the group's own Proposals are numbered without it (#123), the chat bot never claims it, so it never gets a thread, and it carries no Dispatch (#112). A group that has dissolved, or isn't founded yet, opens none. `seatIn(group, coalition)` names the seat a group holds there.
- **What a group owes** (`resultsToReport(group, coalition, seatKey)`). The `group-result` bodies to post from a participant bound to the seat: on the genesis, its reconcile outcome once final, or `fail` if the genesis's name, title or Atoms differ from the target it passed; then each motion its seat decides, once its own vote is final, a lapse as `fail`. Only while results still count, only what the coalition hasn't recorded yet, and nothing once it is declined. Each body is the motion, the seat and the result, and nothing else.
- **What a group sees** (`resultMismatches(group, coalition, seatKey)`). The recorded results for its seat that differ from its own decided result, and both sides of a contested seat, each with the participant who posted it, so the group can talk it out.
- **Privacy.** A coalition log holds group names, motions, its Documents, participants' coalition names, seat public keys and one pass or fail per group, never a ballot, score, count, note, secret or group key (`properties.test.ts` builds every result a group with canaries owes, and finds none of them). The coalition, inner and seat secrets live only in member groups' sealed logs, and the coalition checks only the seat, never a person's level in their group, which would link identities.
- Golden vectors: `vectors/coalition-*.json`, each with a coalition log and member groups' logs (`{name, logs: {coalition, A}, relayNow, expect, report?, mismatches?, unchangedWithout?}`), and the fast-check properties that a motion's outcome doesn't depend on the order distinct seats' results arrive in.
- **Push** (#99). A ballot that closes a motion early in a group wakes it, as for any Proposal (`wakeFor`). An outside motion has no proposer in the group, so `nudgesFor` schedules none for it: #120 adds its wakes.
- **Not yet:** the card, sync, reporting and admission (#114), screens (#120), followers (#124), the room (#125), nesting (#122) and promotion (#126). Deferred past the MVP: changing the threshold, competing versions on a motion, a group leaving a coalition, coalitions across relays (ordering by seq relies on one relay's counter), and new coalition secrets when someone leaves a member group (ADR-0074, ADR-0075 §1).

### Capabilities

`can(state, member, capability)` is the only permission check, and it's false for non-members (#63). It reads the member's level through `LEVEL_CAPABILITIES` in `client/src/engine/capabilities.ts`, the one map from levels to capabilities ([ADR-0003](../adr/0003-three-tier-involvement-levels.md), [ADR-0021](../adr/0021-level-names-and-self-selection.md), #90):

| Level (id) | Capabilities |
|---|---|
| Member (`member`) | `read`, `see-roster` |
| Collaborator (`collaborator`) | `read`, `see-roster`, `vote`, `vouch`, `invite` |
| Co-Creator (`co-creator`) | `read`, `see-roster`, `vote`, `vouch`, `invite`, `propose`, `dispatch` (#112) |

- Each person chooses their level at Join and changes it with a `level` event whenever they like, and the change takes effect at once. Until their voting rights arrive, every level grants only a Member's capabilities (#101, §4, Vouches and the wait before voting).
- Every level holds `see-roster` until the hidden roster returns (ADR-0074, §12).
- `wouldVote(state, member)` decides who enters a Proposal's eligible set: the member holds voting rights (#101) and their level grants `vote`. It ignores suspensions, so a suspension never shrinks the electorate (ADR-0075 §3).
- **Stewards** (#102, #117). Holding a steward seat adds `suspend` and `narrow` to the holder's level, unless they're suspended. While a member's suspension runs, at `state.at`, `can()` grants them only `read` and `see-roster`, whatever their level or seat.
- Code never compares level names. Only `capabilities.ts` and the golden vectors spell out a level id, and a test fails on one anywhere else in `src/`. Screens take ids from `LEVELS` and labels from the messages module, in `LEVELS` order.

## 5. Tally

`tally({eligible, versions: [{id, scores}], bar})` returns `pass` with the winning version, `fail` or `lapse`, each carrying the `bar` it was tallied at (#63, #94). The bar is the Proposal's class's, `rules.bars[class]` (§4). It uses integers only: no floats, division or rounding. For each version, `n` is its number of scorers, `sum` their total, and `zeros` the number of 0s.

1. **Quorum** (ADR-0073, `rules.quorum`). A version is at quorum when `n ≥ 1`, `n ≥ min(eligible, 3)` and `100·n ≥ 30·eligible`. That equals min(eligible, max(3, ⌈0.3 × eligible⌉)) scorers. Each version needs its own quorum, at every bar.
2. **Pass.** A version at quorum passes its bar `{avgAtLeast, zerosUnderPercent}` when `sum ≥ avgAtLeast·n` and `100·zeros < zerosUnderPercent·n`:
   - the ordinary bar, the consent floor (ADR-0002), is `{2, 10}`: `sum ≥ 2·n` and `10·zeros < n`;
   - the entrenched bar (ADR-0015 §2) is `{3, 5}`: `sum ≥ 3·n` and `20·zeros < n`.
3. **Winner** (ADR-0004). Among passing versions, the higher average wins (compare `sumA·nB` with `sumB·nA`), then fewer zeros, then the earlier version.
4. **Outcome.** If no version is at quorum, the vote lapses. If some are at quorum and none passes, it fails.

The vectors in `client/src/engine/vectors/` pin the edges:

- an average of exactly 2.0 passes, and exactly 10% zeros fails;
- a 2-member group passes with 2 of 2 ballots;
- at 11 eligible, 3 scorers lapse and 4 meet quorum; at 15 eligible, 4 lapse and 5 meet it;
- a three-way tie goes to the earliest version;
- a late version that only 2 of 10 eligible members score can't win, because it never reaches quorum (#72);
- at the entrenched bar (#94, `bars-entrenched-edges.json`), an average of exactly 3.0 passes and 2.95 fails; one 0 among 20 scorers (exactly 5%) fails and one among 21 passes; an average of exactly 2.5 with no zeros fails, and passes the ordinary bar (`bars-ordinary-pairs.json`); a vote below quorum lapses; and a version under 5% zeros beats a higher average with more.

Every ballot set that passes the entrenched bar passes the ordinary one, and neither outcome depends on the order ballots arrive in (`properties.test.ts`).

A lapse reads "Not enough people weighed in. This isn't a no." ([ADR-0069](../adr/0069-lapses-celebration-relational-pilot.md)), and Propose again starts a fresh Proposal with a fresh window (#74).

**What the screens read** (#74). `tallyDetail(input)` (`client/src/engine/tally.ts`) returns `{bar, versions, outcome}`, and `tally(input)` is its `outcome`, so the two can't disagree. Each version carries `{id, scorers, sum, zeros, quorum}` and the flags `atQuorum` (`scorers ≥ quorum`), `averageMet` (`sum ≥ avgAtLeast·scorers`), `zerosMet` (`100·zeros < zerosUnderPercent·scorers`) and `passes` (all three), at the input's bar. The average and zero flags are false until someone has scored, and `quorum` is the count above, at least 1, found without dividing. `proposalTally(proposal)` (`fold.ts`) tallies a folded Proposal's ballots at the bar its outcome carries, the one its class set, as the fold settles every outcome. The consent meter and the result read only these, so they draw each Proposal's own lines and `src/app` holds no threshold numbers. `client/src/app/format.ts` turns them into words in whole-number arithmetic: an average floors to one decimal, a share of zeros floors to a whole percent, and a shortfall rounds up and is never "0.0", so an exact average of 1.96 reads "1.9 · Short by 0.1" against the consent floor, never the line itself.

**Coalition motions** (#100, ADR-0036). A coalition never tallies ballots: each member group tallies its own, at the motion's bar, and `coalitionOutcome({seats, passes, fails, expired})` (`client/src/engine/coalition.ts`) decides over N snapshot seats, in integers. Up to 4 seats it passes when all pass and fails at the first fail. From 5 it passes once `3·passes ≥ 2·N` and fails once `3·(N − fails) < 2·N`. Once expired, at deadline + 10,080 minutes, every missing result counts as a fail. A fail wins if the counts ever say both, which distinct seats never do. So at 4 seats 3 passes and a fail fail; at 5, 4 passes pass before the fifth reports and 2 fails fail; at 6, exactly 4 passes pass (`vectors/coalition-thresholds.json`).

Restored (§11): removal's own bar (#115), and priority votes (#107).

## 6. Relay API

#62 builds it: FastAPI on Uvicorn, with SQLite in WAL mode ([ADR-0028](../adr/0028-relay-fastapi-sqlite.md)), behind Caddy on one VM ([ADR-0041](../adr/0041-digitalocean-relay-hosting.md), #68). The relay stores opaque blobs by mailbox id and returns them in order with their receipt minute. The unguessable mailbox id is the only capability: there are no accounts or tokens (ADR-0073).

| Method | Path | What it does |
|---|---|---|
| `PUT` | `/v1/mailbox/{id}?ttl_days=N&wake=1` | Stores one raw `application/octet-stream` blob and returns `201 {"seq": n}`. `wake=1` (optional) asks for a push |
| `GET` | `/v1/mailbox/{id}?after=S&limit=L` | Returns `{"records": [{"seq", "received", "data"}], "now", "instance"}` |
| `GET` | `/v1/health` | Returns `{"status": "ok"}` |
| `GET` | `/v1/push/key` | Returns `{"vapid_public_key": k}`: the relay's P-256 point, uncompressed, as 87 unpadded base64url characters (#89) |
| `PUT` | `/v1/push/{id}` | `{"endpoint": url}` registers a push endpoint under the mailbox for 30 days, or refreshes it, and returns `204` |
| `DELETE` | `/v1/push/{id}` | `{"endpoint": url}` forgets it, and always returns `204` |
| `POST` | `/v1/push/{id}/nudge` | `{"not_before": minute}` schedules a wake in that relay minute, or now if it has passed, and returns `204` |
| `PUT` | `/v1/backup/{id}` | Stores one raw `application/octet-stream` backup, replacing any earlier one, and returns `204` (#97) |
| `GET` | `/v1/backup/{id}` | Returns the backup's bytes as `application/octet-stream`, or `404 {"error": "not_found"}` |

- **PUT.** The id matches `^[A-Za-z0-9_-]{43}$`, the body is exactly 1,024, 4,096, 16,384 or 65,536 bytes, and `ttl_days` is 1–30. `Content-Length` is required and at most 65,536, and the relay checks it before reading. Anything else gets a 4xx and stores nothing. Once the database and its WAL pass `RECONCILE_RELAY_MAX_DB_BYTES` (default 1 GiB), a PUT gets `507 {"error": "storage_full"}`. Then a PUT that would take its mailbox's unexpired blobs past `RECONCILE_RELAY_MAX_MAILBOX_BYTES` (default 64 MiB) gets `507 {"error": "mailbox_full"}`, so no one mailbox can fill the relay (#141). Both caps are checked on the declared length before reading, and the mailbox cap again just before the insert. A full mailbox makes room only as its blobs expire.
- **GET.** `after` is at least 0 (default 0), and `limit` is 1–100 (default 100). Records come in ascending seq order, after `after`, unexpired, with `data` in standard base64. An unknown mailbox returns an empty list, never a 404. The relay reads `now` before it selects, so every record a response leaves out has `received` ≥ `now`.
- **Order and time.** `received` and `now` are relay minutes, ⌊Unix seconds / 60⌋. `seq` only grows, even after a purge empties a mailbox. `instance` is 16 random bytes made with the database, so a client can tell when it meets a fresh relay. The relay is trusted for this order and time (ADR-0073), and for nothing else.
- **Storage.** One table, `blobs(mailbox, seq, blob, received, expiry)`, plus a `meta` row for `instance`. `expiry` is the UTC day of receipt plus `ttl_days` plus 1, and a row expires once today reaches it. A GET skips expired rows, and a daily purge deletes them. Push adds two tables (#89): `push_subs(mailbox, endpoint, expiry)` and `nudges(mailbox, due)`, both `WITHOUT ROWID`, keyed on all but `expiry`, with no push keys, timestamps or counters. An index on `(mailbox, expiry, length(blob))` sums a mailbox's bytes for its cap without reading a blob (#141). Any new column needs an ADR.
- **Backups** (#97, ADR-0043 §3, [ADR-0072](../adr/0072-protocol-details-for-decomposition.md) items 13 and 14). The id follows the mailbox rule (else `400 invalid_backup`), and the body is `application/octet-stream` of exactly 65,536, 262,144, 1,048,576, 4,194,304 or 16,777,216 bytes. `Content-Length` is required and at most 16,777,216, checked before reading, as for a blob, and the relay's `storage_full` applies; the mailbox cap counts blobs only. One table, `backups(id, blob, expiry)`, `WITHOUT ROWID`, keyed on `id`, every column `NOT NULL`, with an index on `expiry` for the purge and no receipt time. A PUT replaces the row, and `expiry` is the UTC day of the write plus 181, so a backup is kept 180 days after its last refresh. A GET doesn't refresh it, skips it from its expiry day, and the daily purge deletes it. There is no DELETE: a backup goes when it expires.
- **Push** (#89, [ADR-0012](../adr/0012-content-free-push.md)). It is on only when `RECONCILE_RELAY_VAPID_KEY` names a PEM P-256 private key, which deploy.sh makes once on the VM ([`deploy/README.md`](../../deploy/README.md)). `RECONCILE_RELAY_VAPID_SUBJECT` must then be `https://<domain>` or `mailto:<address>`, never `localhost` or an IP address, or the relay won't start. Without a key, every push route returns `404 {"error": "push_unavailable"}` and `wake` does nothing.
  - **Requests.** The push routes take `application/json` (else 415) with a declared `Content-Length` of at most 2,048 bytes, checked before reading. A body is one UTF-8 object holding exactly its one key, of its type, with no duplicate key (else `400 invalid_request`). Mailbox ids are checked as for a blob. A push PUT or nudge gets the blob PUT's `storage_full`; a DELETE doesn't, and the mailbox cap counts blobs only. `wake` is `1` or absent (else `400 invalid_wake`, checked before the body).
  - **Endpoints.** At most 1,024 bytes of printable ASCII: `https`, no userinfo, fragment, backslash or space, port absent or 443, and a lower-case host that is `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com`, or under `push.apple.com` or `notify.windows.com`. Every failure gets the same `422 {"error": "push_endpoint_rejected"}` and stores nothing. `expiry` follows the blob rule with 30 days, and a re-PUT refreshes it. A mailbox holds at most 100 endpoints; the 101st evicts the one expiring soonest, never itself.
  - **Nudges.** `not_before` is a relay minute from 0 to now + 43,200 (else `400 invalid_not_before`). A mailbox holds at most 50 pending nudges (else `429 too_many_nudges`), and a repeated minute is no new one. `wake=1` adds a nudge due in the blob's own `received` minute once the blob is stored, past the cap, and only if the mailbox has a live endpoint to wake.
  - **Sending.** Every 15 s the relay takes and deletes the due nudges, then sends one empty POST to each live endpoint of those mailboxes, each endpoint once however many of its mailboxes are due. The headers are exactly `TTL: 86400`, `Urgency: normal`, `Topic: reconcile` and RFC 8292's VAPID `Authorization` (`aud` the endpoint's origin, `exp` 12 hours on, `sub` the subject), over `httpx2` with no redirects, no cookies, no environment, 5 s to connect and 10 s in all. 201 or 202 succeeds, 404 or 410 deletes the endpoint from every mailbox, and anything else, an exception included, keeps it with no retry. Nothing is logged. The daily purge deletes expired endpoints, and nudges left more than a day overdue.
- **Never.** Errors are a constant `{"error": "<code>"}` that never echoes input. There are no docs routes, no debug route, no CORS (the app and relay share one origin) and no request logs. The outermost ASGI middleware sets `scope["client"]` to `None` and deletes forwarding headers before routing. Uvicorn runs one worker with `--no-access-log --no-proxy-headers --no-server-header`. The relay's only outbound requests are pushes.

## 7. Sync

#64, #71 and #73 build it.

- **Mailboxes** (#110; ADR-0019, ADR-0074). Each group writes to one mailbox a week, derived from its current epoch's secret and the relay week (§3, #98), so the relay sees an unrelated id each week; each invite gets a short-lived one of its own (ADR-0073). Records read from any of an epoch's weekly mailboxes are tagged with its epoch. Group events are posted with `ttl_days=30`, so the relay keeps them 30 days (ADR-0057), and 5 weeks cover everything it still holds. Push registrations and nudges take their mailbox only from `mailboxAt(group, minute)` (`client/src/store/mailbox.ts`, #99): the current secret's id for that minute's week, so a key change moves them to the new epoch's mailboxes and each week to its own. Per-member mailboxes, batching and jitter stay deferred (ADR-0073).
- **Polling.** While the app is visible, sync runs every 3 seconds, and at once on focus or when the browser comes back online. After a failure it doubles its wait, up to 30 seconds; coming back online resets the wait (#168). There's no WebSocket.
- **Each pass:**
  1. GETs first (#110): the mailbox of the week of the group's last relay minute, or week 0's, which no one writes to, while the group has none yet (a new group's first pass). That GET's `now` gives this week, so a device back from a long absence never writes to a stale week;
  2. posts the outbox in order to this week's mailbox, removing an entry only after a 2xx, so an event made offline survives a reload and goes out exactly once. A `proposal`, or a `vote` after which this device's fold closes its Proposal early, goes with `wake=1` (`wakeFor`, `client/src/engine/wake.ts`, #99), and so does a `dispatch` (#112), whether or not this device's own push is on;
  3. reads each week `pollWeeks` names, ascending: last week's mailbox and this week's, so a record that reached last week's as the week turned is still read, and, when the last sync fell in an earlier week, each week since, once, back to the last 5. Each mailbox is read after its own cursor (the first GET stands for its week, read on past what it held when this device has posted there), paging until a page holds fewer than `limit` records. The pass opens each blob, skips one that won't open, and adds each record that verifies and whose event id isn't in the log yet, the weeks' records merged by seq. A record read in a later pass than records of higher seq, as one that reached last week's mailbox after this device read it, goes before them: within one relay, a higher seq never arrived earlier (`client/src/store/logOrder.ts`);
  4. saves each mailbox's cursor, by its id, for the last 5 weeks, dropping older ones; `relayNow`, the earliest of its GETs' `now`s, so no record a GET left out arrived before it; `instance`; and the time of the last successful sync. The group's base `cursor` is where a mailbox with no cursor of its own is read from: 0 from creation, the invite's highest seq after a join, and the key change's seq after a move to a new epoch;
  5. reads the new epoch's mailboxes at once when the pull moved the group to a new epoch (§4, Encryption keys and a new group key; #98), and queues the member's `kx` when the fold has none;
  6. runs the chat bot for the group (§4, Chat bot; #119), which claims and posts only while the group has its bot on and hasn't dissolved, after `settleDissolve` (Dissolve, below), and never once the loop is halted (#78). Nothing it does changes whether the pass succeeded;
  7. keeps the group's front door (§4, Front door; #121): its page when one is due and its inbox while the door is open in effect, and a closed page for each door no longer open, a dissolved group's included, never once the loop is halted. Nothing it does changes whether the pass succeeded;
  8. posts the push nudges for this device's own open Proposals (§7, Push), each once, and none for a read-only archive (#108). Nothing it does changes whether the pass succeeded either.

  After a pass in which every group synced, each group with a key change due gets the duty (§4). While one is due, the outbox sends only `key-rotate` and `leave`. A read-only archive (Dissolve, below) gets neither: no key change is due once a group has dissolved, and an archive writes none and posts no `kx`. Then, unless the loop is halted, push upkeep runs (Push, below), then the replies to the front-door applications this device sent (§4, Front door; #121), which runs on a device in no group too, and last the relay backup's refresh (`afterPass`, §3 Relay backup, #97), so both see each group at the epoch its key change moved it to; the refresh may send the day's largest request, so it waits for the rest.
- **A new `instance`**, at a pass's first GET, means a fresh relay database: the pass reads every mailbox from 0 and posts the outbox to it, its pull starts every cursor over and puts its records after the whole log, since the fresh relay's seqs start again from 1, and dedupe by event id keeps any event from folding twice. A pass that meets another instance after its first GET fails, and the next starts over.
- **Leave** (#77). Leave this group signs a `leave` and `markLeaving` queues it after the outbox and marks the group `leaving`, in one store change. From then on the store queues nothing more for the group, and the screens read "Leaving…", with proposing, voting, level changes and Copy invite link turned off. Once a pass's PUT of the leave returns a seq, `purgeGroup` deletes every record of the group from the device in one transaction (its log, cursor, outbox, keys, secret, drafts and flags all live in its one record), and the pass reads nothing more for it. Offline, or while the relay refuses it, the leave waits in the outbox across reloads. Clearing the group from the person's other device when it syncs a leave made elsewhere is deferred: they tap Leave there too.
- **Dissolve** (#108, `client/src/store/archive.ts`). After a pass that brought new records or a new relay minute, `settleDissolve` folds the group. Once a `dissolve` has folded, `markArchived(groupId, 'dissolved')` drops the outbox, any drafts, any leave, the chat bot's claims and what it learned of the webhook (#123), and marks the group archived, in one store change; from then on the store queues and claims nothing for it, and a pass sends and reads nothing for it and its chat bot posts nothing, so no request names its mailbox again and the relay's copy expires on its 30-day schedule (ADR-0057). There's no relay route to delete it: a `DELETE` keyed by the mailbox id would let any member, or anyone holding an unexpired invite, erase events other devices haven't fetched. Before that, a device whose member's `dissolve` the fold would take, folding a dissolve Proposal's final pass, queues one, unless one is queued already or the group is leaving. Erase's halt (#78) waits for a running pass, whose group still settles, since that touches only the store, and runs no chat bot after it. #115 reuses `markArchived` for removal.
- **Dissolved archives keep time on the device** (ADR-0075 §5). No relay time arrives after a dissolve, so at each launch, before syncing, `sweepArchives` acts on each archive by the device's own clock: with `wipe`, the first launch at least `WIPE_DAYS` (7) × 1,440 minutes after the dissolve's `received` runs `purgeGroup`, so everyone sees the result first; without, the first launch at least `ballotExpiryDays` (30) × 1,440 minutes after it clears the archive's ballots and notes in one change: the store keeps the state the device last folded with no ballot on any Proposal, and each decided Proposal's totals and outcome from the device's own tally (`clearArchive`), and drops the log. The screens show that kept state from then on. This is a device-local stand-in for #111's expiry, which needs a `result` in the log, and should converge on it. Remove from this device runs `purgeGroup` at any time.
- **Folded state uses relay records only.** An event in the outbox shows as pending and never in folded state (#66). While it waits, its screen reads "Sending…" if the last sync reached the relay, and "Saved on this device. It will send when you're back online." once a sync has failed; then "Sent" once it leaves the outbox.
- **Joining with full history** (#73, `src/invite/envelope.ts`). An invite envelope is a header blob followed by chunk blobs, each sealed under the invite key with the group's `Seal` and posted to the invite mailbox with `ttl_days=1`, the header first. The relay's TTL is the only expiry, so the link lives 24–48 hours.
  - The header is JSON `{groupSecret, epoch, preview: {groupName, inviterName, documentTitle, excerpt}, token, chunkCount}`, with the group's current secret in base64url and its epoch (#98). A header without `epoch`, from before #98, reads as damaged. The excerpt is the first Atom as plain text, its Markdown taken out, cut to 280 code points plus "…". The group name, inviter name and title are cut to 120 code points plus "…" likewise, so a header always fits one small blob. A reader refuses any field past its limit.
  - Chunks carry the relay-accepted log in seq order, never the outbox, as big-endian `seq (8 bytes) ‖ received (8) ‖ epoch (4) ‖ length (4) ‖ record` entries (the epoch since #98), packed up to the `Seal`'s 65,492 bytes. `received` travels with each record, because deadlines depend on it. The 64,000-byte record cap means every record a device makes fits.
  - Copy invite link copies the link only after every PUT succeeds. Otherwise it says so and copies nothing.
  - Opening is all or nothing. The app reads every blob in the invite mailbox: an empty mailbox (an expired link), a missing or extra blob, a blob that won't open, a header or chunk that doesn't parse, or entries with no genesis all show the expired-or-damaged line. A seed that doesn't parse shows it with no request at all.
  - A secret past epoch 0 must be the one its epoch's key change in the entries commits to, or the link reads as damaged (#98).
  - Nothing is stored before Join. Join makes a signing keypair and an encryption keypair, takes the group id from the entries' genesis, imports the entries through the same verify and dedupe path as sync, sets the cursor to their highest seq, keeps the invite GET's `now` and `instance`, and queues the `join` with the token.
  - A device already in the group (the same genesis id) merges in the entries it lacks, each in seq order among the ones it has, and refolds, with no new key and no join. When the envelope's epoch is later than the device's and its secret matches that epoch's commit, the device takes it up as a switch does (§4, #98), so a device that missed a new key gets back in.
- **Catching up** (#73). When a sync succeeds more than 28 days after the previous one (by the device clock), the device sets a persisted `missingHistory` flag, and Group home says "Some history may be missing on this device. Open a new invite link from your group to catch up." Only a merge clears it, because the last sync's age resets the moment sync resumes.
- **Requests.** `src/net/relay.ts` calls `/v1` on the same origin with `credentials: 'omit'`, `referrerPolicy: 'no-referrer'` and `cache: 'no-store'`. The service worker never caches `/v1` (#76).
- **Offline** (#76). The app installs from `manifest.webmanifest` (`id`, `start_url` and `scope` all `/`, `display: standalone`), with icons at 192, 512 and 512 maskable, plus a 180 `apple-touch-icon`. A service worker, `/sw.js`, keeps the build on the device:
  - The build writes it from `src/net/sw.ts` (`client/plugins/serviceWorker.ts`), as one classic script holding the list of every file the build writes (fonts and `public/` included, index.html as `/`) and a version that hashes them all. It's served from the app's own origin, so the CSP needs no change. A small hand-written worker stands in for `vite-plugin-pwa`, whose `workbox-build` fails `npm audit` with no patched release.
  - Install fetches every listed file into a cache named for the version, revalidating each with the server. Activate deletes older versions' caches. Fetch answers every page load with the app shell and each listed file from that cache, and leaves everything else to the network. Nothing under `/v1` is cached or answered from a cache, and nothing is cached at run time.
  - It registers in production only, after the page loads, from a bundled module: nothing is inline.
- **Install first** ([ADR-0029](../adr/0029-install-first-indexeddb.md), #76). On an iPhone or iPad, nothing creates keys until the app runs from the Home Screen. An Apple touch device has `iPhone`, `iPad` or `iPod` in its user agent, or `Macintosh` with more than one touch point (iPadOS); it's installed when `(display-mode: standalone)` matches or `navigator.standalone` is true (`src/platform/installGate.ts`). Once the pilot notice is accepted, and at each launch after, the app calls `navigator.storage.persist()` (`src/platform/persist.ts`: granted, denied or unavailable, never a throw), and Start says so when the browser may still clear its data.
- **Linking a device** (#96, §3). Every PUT of the handshake and the bundle uses `ttl_days=1`. While a link screen is open, it looks at its mailbox at once and then every 2 seconds, and keeps trying while the relay is out of reach. Nothing in a link touches a group's mailbox: the new device's first sync, once the groups are in, is a group's first request from it.
- **Shares by link** (#105, §11). `keepSharesAlive` runs once at each launch, beside the sync loop and never in its pass, so it has no place in the pass's order: a share has its own seed, mailbox and keys, tied to no group, so no key change, freeze while one is due, dissolve or push upkeep touches it, and it touches none of them. A share posted while a key change is due posts as usual; the relay backup's refresh still waits for the change to land, and its copy then holds the share as last posted.
- **Push** (#99, [ADR-0012](../adr/0012-content-free-push.md); the relay's side is §6). Opt-in, one switch per group, all off to start (§8.12), with no content anywhere:
  - **The notification.** The service worker answers every push the same way, never reading its data: it closes any open notification tagged `reconcile` (Safari ignores tag replacement), then calls `showNotification("Something new in Reconcile", { tag: 'reconcile' })` with no other option, and never sets the app badge (`client/src/sw/notify.ts`). A tap closes it and focuses a Reconcile window, or opens `/`, and the app syncs as it comes to the front. The app closes these notifications whenever it becomes visible.
  - **Turning a group on** runs inside the tap: `Notification.requestPermission()` before anything is awaited, then `GET /v1/push/key` (never a build constant) and `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`, then a `PUT /v1/push/{mailbox}` for each mailbox `mailboxAt` gives from now to 30 days on and, before them, for the week of each Proposal still open, where its nudges wait (#110). Only once the relay has taken it does the store keep the group's `push` registration (endpoint, mailboxes, `instance`, relay minute), which is the switch. A denial stores and sends nothing.
  - **Turning one off** clears the registration at once and sends a best-effort `DELETE`; once no group is on, the device calls `unsubscribe()`. Leave fires a `keepalive` `DELETE` just before `purgeGroup` and doesn't wait for it.
  - **What wakes.** A Proposal, a ballot that closes one early, and a Dispatch (#112) go with `wake=1` (§7, Each pass). A Dispatch a Proposal carries needs no wake of its own: it rides the result's. For each of its own open Proposals, the proposer's device posts two nudges once each, once the Proposal is in folded state: `deadline − 1440` (closing soon) and `deadline` (its result, when no ballot closes it early), each to the mailbox of the week the Proposal was received in, `mailboxAt(group, received)` (`nudgesFor`, `client/src/engine/nudges.ts`). Never the deadline's own week (#110): its minute less the vote window is the Proposal's receipt, so a nudge filed there would tie two weeks' ids together at rest. It keeps them in the group's `nudged` list. A 4xx answer is final; anything else is tried again on a later pass. Cancelling the deadline nudge after an early close is deferred: one extra wake carries nothing.
  - **Upkeep**, after each pass in which every group synced: each group with push on is registered again 7 days after the relay last took it, or when the subscription's endpoint, the relay's `instance` or the group's mailbox set changes, the old endpoint `DELETE`d first. With weekly mailboxes (#110) the set changes as this week leaves its front and a new week enters its 30 days, about twice a week, so each change re-`PUT`s every week the registration names and `DELETE`s a week it no longer names: last week's, once no open Proposal was received in it. One endpoint under each of them already links a group's weekly ids at the relay (ADR-0075 §2), so the re-`PUT`s link nothing more. When the endpoint stays and the mailbox set changes, each mailbox the group no longer has is `DELETE`d once the new ones hold the endpoint. When `/v1/push/key` differs from the subscription's `applicationServerKey` (a rebuilt relay), the device unsubscribes and subscribes again. When the subscription is gone and notifications are no longer allowed, every group turns off here. After a failure, upkeep rests for an hour.
  - **Across a key change** (#98). `mailboxAt` derives from the group's current secret, so once a switch moves the group to a new epoch, the next upkeep `PUT`s the endpoint under the new epoch's weekly mailboxes and `DELETE`s it from the old ones. A phone whose app stays closed stays under the old mailbox, and sleeps through what the group posts, until its app next syncs. A `key-rotate` asks no wake, so nobody who left is woken by it, and what wakes is unchanged across epochs.
  - **A dissolved group** (#108) sends no push request at all: no wake, no nudge (`nudgesFor` gives none once a group has dissolved) and no upkeep. Its registration and any nudge already scheduled are left to expire at the relay, within 30 days, since a `DELETE` would name the mailbox after the dissolve; `markArchived` forgets the registration on the device, Settings shows no switch for a read-only archive, and turning one on fails before anything is sent. Leave's `keepalive` `DELETE` still goes while a key change holds the outbox, since a `leave` passes the freeze.
  - **Personal Documents** (#93) get no switch: they aren't groups, and nothing about them reaches the relay.
  - **What goes out.** Push request bodies hold only `{"endpoint"}` or `{"not_before"}`. The endpoint goes only to the relay, under the mailboxes of groups the person turned on. A backup file never holds a registration: an endpoint belongs to one device.
- **Updates** install in the background and apply on the next launch, with no prompt (ADR-0057 as cut by ADR-0073, #76). The worker never calls `skipWaiting()` or `clients.claim()`, so a new version takes over once every Reconcile window has closed.

## 9. Privacy rules

Every issue, foundation or restored, keeps these. The threat model is [`12_Security_Privacy_Threat_Model.md`](../plan/12_Security_Privacy_Threat_Model.md).

- **No accounts and no IP logs.** The relay drops client addresses and forwarding headers before any route runs. Caddy discards its logs, and the VM keeps its journal in memory only (#62, #68). Whoever runs the relay can still see connecting IP addresses and timing live, and the pilot notice says so.
- **Padded, sealed blobs.** Everything a device sends the relay is a sealed blob of one of the four sizes, under a mailbox id derived from a secret only members hold. The author and the signature sit inside the seal (ADR-0019). A relay backup (#97) is one sealed blob of one of five sizes under an id derived from a key only the person's devices, backup file and, after #109, chosen contacts hold, linked to no mailbox, written at most once a relay day. Uploads come from the same IP address as the device's group syncs, so whoever watches the relay live can tie the backup to those groups (ADR-0075 §2).
- **The relay is trusted only for order and time** (ADR-0073). It can't read, forge or link anything it stores.
- **A front door shows no one** (#121, ADR-0038). Its page carries the group's name, an excerpt and, only if chosen, a count, never a member's name, key or id. Its secrets live only in the sealed log; applications are sealed to its key and replies to a key only the applicant's device holds, and an applicant gives no contact details. Doors aren't listed anywhere (ADR-0038's index stays deferred).
- **Secrets stay after `#`.** Invite seeds, group secrets and share seeds travel only in the URL fragment, and the app removes invite seeds and group secrets from the address bar once read (#65, #73, #76). A share link's seed stays there, so a reload reads it again: it opens one personal Document, read-only, and nothing of anyone's groups (#105). A linking code (#96) never enters a URL at all: it's shown, scanned or pasted, and held in memory while its screen is open. Beside Copy invite link: "Anyone who opens this link in the next 2 days can read everything this group has written and voted on, and what comes next. Send it directly to the people you're inviting."
- **Open ballots, inside the group only** ([ADR-0010](../adr/0010-open-ballots-with-exit.md)). Everyone in the group sees each other's names and ballots, and nobody outside it sees either. Every level can read ballots and vouches until the hidden roster returns (ADR-0075 §5).
- **Shares carry no content.** Tell your group sends a fixed message, a deadline and the app's address. The Proposal's title goes in only when the person ticks Include the title for that one share, and never for a steward Proposal. A share never carries Document text, a group name, a member's name, a link fragment or a secret, and Web Share gets no `title` field (#77, #113). The one exception is Share link (#105): it hands on a share link, whose fragment is the point, beside fixed words and never the Document's title or text.
- **Nothing third-party.** There are no analytics, telemetry, third-party scripts or third-party fonts. The app calls only the relay, plus the browser's push service once a person turns push on (#99), and a Discord webhook for a group that turned its bot on by Proposal (#119).
- **Script defense.** The CSP `default-src 'self'; script-src 'self'; style-src-elem 'self' 'sha256-…'; connect-src 'self' https://discord.com/api/webhooks/; object-src 'none'; base-uri 'none'; frame-ancestors 'none'` (#68) and `<AtomText>` (#70, §8.6) are the main defense against injected script stealing keys. Its one hash, in full in `deploy/Caddyfile`, allows React Aria's iOS scroll-lock `<style>` and nothing else (#153, [deploy/README.md](../../deploy/README.md#the-csp)); it never allows `'unsafe-inline'`. Atom text never becomes HTML, links are limited to `http:`, `https:` and `mailto:`, and the renderer loads nothing: images are off, so no Atom can make a device fetch. The linking code (#96) needs no change to it: the QR code is an inline SVG, never a `data:` image, and the decoder runs on the main thread, with no `blob:` worker or WebAssembly. No `Permissions-Policy` header is sent, so the camera is the browser's default, the app's own origin, and the page asks for it only after a tap.
- **Local data.** Leave deletes every record of the group from the device once the relay has the leave (#77). A dissolve sends nothing more and ends all traffic for the group; with wipe, each device deletes every record of it a week later, and without, each clears the copy's ballots and notes 30 days later. The composer says no app can stop someone who already kept a copy, a screenshot or a backup file (#108). Erase deletes all of Reconcile's data on the device and makes no network call (#78): `eraseDevice` halts the sync loop, so no request starts after it and the chat bot (#119) claims and posts nothing, and closes the store, since an open connection blocks `deleteDatabase` (another tab's store closes itself when asked). It then deletes every database, the store's and any that `indexedDB.databases()` lists, empties Cache Storage, `localStorage` and `sessionStorage`, unregisters every service worker, and only when all of that succeeded calls `location.replace('/')`, which opens on first run with no groups. The passkey vault goes with the database (#95); the passkey itself stays in the person's password manager, named "Reconcile key", until they delete it there. Erase sends no push `DELETE` (#99): one would tell the relay this phone had just erased. Unregistering the worker ends the push subscription, so the push service refuses the relay's next push to it with 404 or 410, and the relay forgets that endpoint under every mailbox (#89); the relay drops any registration after 30 days in any case. The backup file is sealed, never uploaded, and holds no readable name, text, key or secret. A link's bundle (#96) reaches the relay only sealed under a key the relay never sees, in a mailbox it can't tie to the group, and each device zeroes the link's secrets once it's done. Private drafts live inside the group's record, so both remove them, and nothing ever sends one (#70). Personal Documents live in the same database, so Erase deletes them too, and Leave never touches them (#93). A dissolve's wipe and its clearing leave them alone too (#108).
- **ADR-0074's restored protections:** a new group key whenever someone leaves, with per-member encryption keys (#98; removal joins it with #115); mailboxes that rotate weekly (#110); and ballots and notes that expire 30 days after a decision, leaving a signed result (#111). A new secret leaves a device only inside per-member boxes, so the relay sees one more padded blob and a new mailbox id. Until the rest merge, the foundation runs with ADR-0073's other accepted risks: ballots don't expire, and there are no recovery contacts.
- **Accepted pilot risks,** which the outside review covers ([ADR-0058](../adr/0058-security-review-on-demand.md), #132):
  - the relay is trusted for order and time (ADR-0073);
  - coalition keys don't rotate, and push shows the relay some metadata (ADR-0074);
  - anyone holding a coalition seat secret can block a motion or act in the coalition, push and polling show the relay which groups share a phone, and colluding recovery contacts can skip the wait (ADR-0075).

### Personal page (#93)

ADR-0074 builds the personal page at level 2: a personal mission statement on this device, and a read-only share link (#105). A personal statement may be the most identifying thing anyone writes here, so it stays local-first ([ADR-0001](../adr/0001-local-first-trust-model.md)): it leaves the device only inside the passphrase-sealed backup file (§3), #97's encrypted relay backup, which reuses the same snapshot, and #96's sealed second-device link bundle, which takes the snapshot through `withoutShares` and so leaves out #105's share state. The one other way out is the share link (#105, below), which the person turns on for one Document at a time: then its latest version goes to a mailbox of the share's own, signed and sealed. No group's record carries it, and nothing else sends it anywhere.

- **Store** (`client/src/store/personal.ts`). Store version 4 adds a `personal` object store of `{id, title, text, createdAt, updatedAt}`, plus `share` while the Document is shared (#105), keyed by `id`: 16 random bytes in unpadded base64url. The upgrade adds the store beside the groups and deletes nothing. `listPersonal` lists them oldest first, and `savePersonal` refuses one whose id, title or times aren't well formed (`isPersonalDocument`): a title is trimmed, 1–120 code points by `nfcLength`, and `updatedAt` is never before `createdAt`.
- **Personal** (`#/me`, `client/src/screens/Personal.tsx`), reached from a card on Start, behind `FirstRunGate` like every screen. It lists the device's Documents by title, each opening at `#/me/{id}`, then New document. With none yet, it offers My mission statement with one line, "What do you stand for, and what are you working toward?". Either opens a new id, and nothing is stored until that Document's first save. One line says "They stay on this device. Nothing here is sent to the relay or to your groups, unless you share one by link. A backup file you save includes them.", and a shared Document's card says "Shared by link" under its title (#105).
- **Editing** (`#/me/{id}`, `client/src/screens/PersonalDocument.tsx`). A title field, then the composer's Write and Preview tabs and hint (§8.7), with no why, no link and no Propose, since nobody votes on a personal Document. The first Document on a device starts titled My mission statement, with its prompt line; another starts with a blank title. The text saves as typed about 500 ms after typing stops, and when the editor closes, with "Saved on this device." after each save. Preview renders `normalizeAtomText(text)` through `<AtomText>`, so normalizing never moves the cursor, and #105 normalizes before it posts. A blank title or one over 120 code points is refused, tied to the field, and holds saving with "Not saved yet. Fix the title to save your changes." Each save keeps the first save's `createdAt` and stamps `updatedAt` with the device clock, never earlier than the last stamp. Delete opens an alert dialog, "Delete '<title>' from this device? A backup you saved earlier still has it.", and drops any save still waiting before it deletes, so none can bring the Document back.
- **Not yet:** the relay backup (#97). Deferred past the MVP: a public profile, following a person, listing your groups on your page, and keeping personal Documents in sync between linked devices (restore a backup instead).

### Share link (#105)

ADR-0074's personal page "used as a resume", at level 2: a read-only link to one personal Document, which anyone can open in any browser without installing Reconcile or joining anything. It shows only that Document's latest version, with no follow, no name and no groups. Edits reach the link, and Stop sharing turns it off. The relay's 30-day retention ([ADR-0057](../adr/0057-environments-updates-retention.md)) is the only expiry, so a share that stays on is posted again.

- **Keys** (`client/src/crypto/share.ts`, pinned by `src/crypto/vectors/share.json`, computed outside @noble). Share link makes a random 32-byte seed and a fresh Ed25519 keypair, used for this share alone. The share mailbox id is the unpadded base64url of `hkdf(sha256, seed, empty salt, "reconcile/v1/share-mailbox", 32)`, and the seal key the same with `reconcile/v1/share-key`. The link is `${origin}/#share/${seed}.${publicKey}`, two 43-character base64url values joined by a dot, so both travel only after `#`. The public key is in the link because every reader holds the seal key and could post a copy: only copies signed by the owner's key count. Each share gets a fresh seed, mailbox and keypair, so nothing the relay stores ties it to the person's groups. Sharing the same Document again makes a new link.
- **Copies** (`client/src/share/copy.ts`). A copy is UTF-8 JSON, `{v: 1, n, title, text}` with the text normalized (`normalizeAtomText`), or a tombstone `{v: 1, n, stopped: true}`. It is signed with `sign` under `reconcile/v1/share`, framed as a record (`publicKey ‖ signature ‖ bytes`), sealed with the app's `Seal`, and posted with `putBlob(mailbox, blob, 30)`. A reader parses only exactly these fields. A Document whose record, at the largest `n`, would be over 64,000 bytes can't be shared (`fitsShare`), and a message tied to Share link says so; a shared one that grows past it says its link keeps the last version that fit.
- **Posting** (`client/src/share/shareLink.ts`). Before each post the device reads the share's mailbox and numbers the copy one past the highest `n` there that verifies under the share's key, or its own last `n`, whichever is higher, so restoring an older backup can't roll the link back. A verified tombstone there is final: the device drops the share and posts nothing, so a backup made before Stop sharing can't bring the share back. Posts for one Document run one at a time, so two never take one `n`.
- **The owner's side.** The share state `{seed, secretKey, publicKey, n, lastPostedAt, pending}` lives on the personal record, so the backup file and #97's relay backup carry it (§3); #96's link bundle doesn't, because personal Documents don't sync between devices and two devices posting one share would roll its link back and forth. A linked device starts with every Document unshared, and only the device that made a share can stop it (§3, Second device). Only `updateShare` sets or drops it: the editor's saves keep it, and mark it `pending` when the title or text changed. A restore whose later copy of a Document holds no share keeps the device's, marked pending (`restoredCopy`), so no live link is lost where the person couldn't stop it. Off by default, the editor's Share by link section says, before anything is sent, "Share link makes a link anyone can open in any browser to read this Document's latest version, without joining anything. They see its title and text, never your name, your groups or your other Documents." and "The relay keeps only a sealed copy it can't read. As when your groups sync, it sees this device's internet address while it posts, so someone watching it live could tell this device also uses your groups." Share link saves what was typed, posts the first copy, and only once the relay has it keeps the share and hands the link to `shareOrCopy` with fixed words, "Something I wrote, shared read-only with Reconcile:", never the title or text. Offline, nothing is kept or copied. Beside the link: "Anyone with this link can read this Document. It stops working if you don't open Reconcile for 30 days." Leaving the editor posts a new copy when an edit is pending (`postEdits`), and any failed post sets `pending`. `keepSharesAlive()` runs at each launch and posts the latest copy of every share that is pending or was last posted 20 or more days ago. Stop sharing posts a tombstone, then drops the share, and says "Sharing stopped. People who opened the link may have kept a copy, and earlier copies stay on the relay, still sealed, until they expire within a month." Offline, it changes nothing and says so. The relay has no delete route, and this adds none. Deleting a shared Document stops sharing first, and deletes nothing when it can't.
- **The reader's page** (`client/src/screens/SharedPage.tsx`). `#share/…` renders it outside `FirstRunGate`: a fresh page gets it alone (`SharedRoot`), with no store, sync loop or service worker, and an open app shows it in place of first run. It parses the link, GETs the mailbox (paging) and opens each blob, keeps only copies whose record key is the link's and whose signature verifies, and shows the one with the highest `n`, ties going to the later seq; any verified tombstone means the share has stopped. The title shows as plain text in `<bdi>` and the text through `<AtomText>`, under "Shared with Reconcile. Read-only.", and the tab reads "Shared page · Reconcile", never the Document's words. A tombstone, an empty mailbox, no valid copy and a damaged link all show "This page isn't shared any more, or the link is damaged.", and a damaged link makes no request; a relay it can't reach shows Try again. The page opens no IndexedDB database, makes no key, writes no web storage and starts no sync loop. It leaves the fragment in place, so a reload works, and once the address leaves the link the page reloads into the app.
- **Privacy.** The text leaves the device only padded and sealed (ADR-0019), under a key that exists only after `#` in the link. As with any sync, the relay sees the poster's and each reader's IP address live and doesn't store it. Posts run from the same IP address as group syncs, so whoever watches the relay live can tie the share to those groups (ADR-0075 §2); the disclosure says so. Anyone who read the link may keep what they read.
- **Deferred past the MVP:** following a person, showing their groups or Proposals, short links, view counts and comments.

### Rules the restored features share

These come from ADR-0074's "Rules this needs":

- **Windows** (#94, #106). Ordinary votes run 3–14 days (default 7) and entrenched votes 14–28 (default 14). The deadline is fixed in relay time when the Proposal opens, and early close still applies.
- **Bars** (ADR-0015, #94). Entrenched sections, dissolution and widening an opt-in pass at an average of at least 3.0 with under 5% zeros. Removal has its own bar (below).
- **Rules are fixed at genesis** with ADR-0067's Fellowship defaults (#94, below). The one exception is the opt-ins that [ADR-0040](../adr/0040-group-opt-ins-are-governed.md) governs, the chat bot and the front door: a rules Proposal widens them at the entrenched bar and narrows them at the ordinary bar (#117).
- **Coalitions form by private, group-to-group invitation,** with no public index, and nest up to 3 levels (#100, #122).
- **One more network destination:** a Discord webhook, only for a group that turned its bot on by Proposal. The URL lives only in the encrypted group state (#119). The CSP's `connect-src` allows the app's own origin and `https://discord.com/api/webhooks/`, and nothing else.
- **Recovery uses a random backup key,** and contacts hold Shamir shares of it (#97, #109).
- **A webhook URL is a credential** (#117). It exists only inside sealed group events and in folded state on members' devices, so the relay never sees it readable, and screens show only its last 4 characters. Only `postWebhook` and `getWebhook` (`client/src/net/discord.ts`, #119, #123) call it, and only while the group has its bot on. What a device learns of it (`chatChannel`, #123) is keyed by the webhook's id, never its token.

### Founding rules

#94 builds them in `client/src/engine/rules.ts` ([ADR-0051](../adr/0051-dissolution-and-rule-classes.md), [ADR-0067](../adr/0067-genesis-templates.md), ADR-0074). `DEFAULT_RULES` holds whole numbers only, and `RULE_CLASS` gives each field its ADR-0051 class:

| Field | Default | Class |
|---|---|---|
| `bars` | ordinary `{avgAtLeast: 2, zerosUnderPercent: 10}`, entrenched `{avgAtLeast: 3, zerosUnderPercent: 5}` | entrenched |
| `windows` (days) | ordinary `{min: 3, max: 14, default: 7}`, entrenched `{min: 14, max: 28, default: 14}` | ordinary |
| `quorum` | `{min: 3, percent: 30}` | entrenched |
| `vouches` | 2 (#101) | ordinary |
| `waitDays` | 14 (#101) | ordinary |
| `ballotExpiryDays` | 30 (#111) | ordinary |
| `stewards` | `{firstElectionAt: 3, secondSeatAt: 6, termDays: 182}` (#102) | entrenched |
| `suspensionDays` | 7 (#102) | entrenched |
| `optIns` | `{chatBot: null, frontDoor: false}`: both off (#117) | `opt-in`: widening entrenched, narrowing ordinary (ADR-0040) |

- **Genesis.** Create group writes `rules: DEFAULT_RULES` into genesis, and the fold keeps the result in `state.rules`. A missing field, at any depth, takes its default, so a genesis without `rules` (every one before #94) still founds its group. A field that differs from its default (the text `"2"` differs from the number 2) makes the genesis invalid: the MVP sets no rule but the defaults, so a hand-made genesis can't lower a bar, and a later change to a default must keep accepting the old value. A field this engine doesn't know is left out of `state.rules`, so a newer device's genesis still founds the group, and the engine that knows the field checks it.
- **Classes.** `targetClass` gives each Proposal its class when it opens (§4), and the class picks its bar (§5) and bounds its window: the proposer chooses one within `windows[class]`, and a Proposal without one runs `windows[class].default` (#106). Removal votes ignore `window` and run a fixed 14 days ([ADR-0075](../adr/0075-safeguards-for-the-revised-mvp.md) §3); #115 adds that case.
- **Opt-ins** (#117). A genesis restates them off like any other default, so no group is founded with its chat bot on or its front door open. A rules Proposal changes the standing value afterwards (§4, Opt-ins), and `state.rules.optIns` holds it.
- **Later fields.** #115 adds removal's bar.

### ADR-0075's safeguards

- **Stewards and removal** (§3; #90, #101, #102, #106, #115):
  - A suspension never shrinks the electorate. Eligibility ignores suspensions (#90's `wouldVote`), and a suspended member can vote once the suspension ends, if the vote is still open.
  - A steward holds at most one active suspension, and a steward facing an open recall can't suspend or narrow. The 30-day guard between suspensions of one person runs from the end of the last one.
  - A removal passes when `sum ≥ 3·n` and either `zeros ≤ 1` or `20·zeros < n`, so a single 0 never blocks it. Removal votes run a fixed 14 days, so a suspension that a removal vote extends lasts at most 21 days.
  - "Voting members" means the people who hold voting rights, whatever level they chose, counted by #101's `votingRightsCount`. The bootstrap and the steward thresholds both use it.
  - **Steward seats** (#102): 1 seat under 6 voting members and 2 from 6, with staggered 6-month terms ([ADR-0049](../adr/0049-stewards-and-removal.md)). That's the Fellowship default. A Circle keeps 1 seat until it reaches 10 voting members (ADR-0067, ADR-0072 item 8), but Circles stay deferred (§12), so every MVP group gets the Fellowship seats.
- **Opt-ins** (§3, §5; #117, #121). A steward's narrowing is valid only beside the same steward's open off-Proposal, and lasts until that Proposal closes. `isWider` compares only what outsiders can see or reach, so replacing a webhook or rotating a front door's keys is an ordinary change.
- **Push** (§2; #89, #99, #110). Push is off by default, with one switch per group. The switch's disclosure says that whoever runs the relay can see that one phone is in each group where push is on. The relay keeps each opted-in mailbox's endpoints and due minutes for at most 30 days, and nothing else about push (#89, §6). This is an accepted risk, and #130 revisits it.
- **Recovery** (§4; #78, #96, #97, #109, #118).
  - The random backup key travels in the backup file and in the second-device link bundle, so a restored or linked device keeps the relay backup fresh.
  - The 72-hour wait runs on each contact's device, in relay time from the relay's receipt of that contact's alert.
  - The picker says "Pick people you'd trust with all your groups at once.", and that a contact picked in two groups can tell both names are the same person.
  - Colluding contacts can skip the wait. This is an accepted risk, and #131 revisits it.
- **Coalitions** (§1, §5; #100, #124, #126).
  - A promoted Dispatch counts as passed in its origin group only when that group's own fold holds the passed Proposal with the same id, title, text and ceiling.
  - A coalition speaks only through passed motions.
  - Following a coalition posts nothing, so followers can't see each other.
  - Anyone holding a seat secret can block a motion or act in the coalition. This is an accepted risk, and #129 revisits it.
- **Dissolved archives** (§5; #108). No relay time arrives after a dissolve, so each device clears the archive's ballots and notes 30 days after it, and with wipe erases the archive 7 days after it, by its own clock at launch (§7, Dissolved archives). This is the one place device time decides anything.
